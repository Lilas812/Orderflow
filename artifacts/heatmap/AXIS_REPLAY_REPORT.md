実施日：2026-10-28 UTC（2026-10-29 JST）

## 対象・変更範囲

- `docs/UI_SPEC_HEATMAP.md` 5節と既存の `src/main.ts`、`src/chart/axis-view.ts`、`src/chart/double-activation.ts` を対象に、実保存データの1倍リプレイをPC Chromiumで操作した。
- アプリ実装、正本仕様、依存、Run／デプロイ設定、保存設定は変更していない。上流WSは開発仕様どおり未接続。本番への操作は行っていない。
- 検証用の一時的な観測処理はブラウザ内だけに追加し、終了時にブラウザごと破棄した。データ・通信の差し替えやダミー約定は使用していない。
- 主確認はChromium 140.0.7339.16、1280×900 CSS px、DPR 1。更新間隔と本体resetの追加確認は、既存CDP補助ツールで起動したローカルHeadless Chromium 152、同じ画面寸法で行った。

## 確認手順

1. 既存の `artifacts/heatmap: web` を起動する。開発では保存走査による起動待ちがある。
2. `/?mode=replay&from=1793022000&speed=1&debug=1` を開き、保存列・約定の受信、`loadingRanges === 0`、再生位置の進行を確認する。
3. 価格軸をダブルクリックしてAUTOを有効にする。本体の時間pan／wheel、価格軸の上下drag、時間軸のダブルクリックを行う。
4. 本体・大口板列・VPのダブルクリック、ツールバーの表示リセットを、それぞれ時間位置・倍率を変更した状態から行う。
5. 設定は保存しない。確認後にブラウザを終了し、`/api/status` の下流接続0を確認してから受信プロセスをSIGTERM停止する。

数値は `window.__heatmapDebug` のviewport、currentPrice、replayHeadUs、follow、cachedTradesと、AUTOラベルの可視性を使用した。価格はすべて整数ティック（1ティック＝0.25）、時間はUnix µs。

### 保存約定との独立照合

`LocalStore.readTrades` だけを使い、initialize／flush／書込を行わず保存ファイルを読んだ。ブラウザの集計結果を期待値として使わず、対象時間 `[startUs, startUs + durationSec × 1e6)` の全約定からmin／maxを別計算した。

期待中心＝(min＋max)÷2、期待span＝max(20, (max−min)÷0.8)。

### 更新間隔の観測方法と限界

最初の6.2秒の測定ではBROWSE中でcachedTradesが一定だった。また、タイマー呼出しには1秒未満で起きた再試行も含まれていた。この測定だけでは「新しい約定を受信中の成功fitは最大毎秒1回」を証明できないため、合格根拠には使っていない。

追加確認では実HTTP配信の同じアプリを使い、ブラウザ内の `setTimeout` を観測した。AUTOのfitを呼ぶ既存コールバックだけを対象に、実行中に同じコールバックのタイマーを再予約した場合を早期再試行として分離した。既存処理はfitの戻り値がnullのときだけその再予約を行う。観測処理は元コールバックを1回だけそのまま実行し、時刻や約定は変更しない。

- 成功fit：13回。連続開始時刻差の最小1000.0ms、最大1000.4ms。
- 再試行：2回。これを成功fit数に含めない。
- 受信観測：performance時刻4934.1→13442.7ms、replayHeadUs 1793022003000000→1793022011000000、FOLLOW=true／AUTO表示のままcachedTradesが743件増加。
- その後、6回の短時間panを行ってAUTO維持と再fitを確認した。
- 計測はコールバック入口・出口の時刻であり、内部fitの瞬間をナノ秒精度で測ったものではない。観測精度内の間隔と、`AutoPriceScale.fit` が前回成功から1000ms未満を拒否する条件を合わせて判定した。FPSからの推定ではない。

### 全体reset

各経路で時間zoom／panなどにより表示を変更してAUTOを有効にした後、別々にresetした。すべて時間幅600秒・価格幅160ティック・FOLLOW=true・AUTO非表示・設定値不変。

大口板・VP・ツールバーでは同じ観測ターンの中心とcurrentPriceが一致。本体の初回撮影では読取の間に約定が進んだため、追加確認で、本体の既存dblclick処理より後に実行される観測リスナーを付けて同じJSタスク内で記録した。中心117052＝currentPrice117052、再生位置1793022015000000、時間開始1793021535580524だった。処理の呼出し自体はCDPのマウス入力によるダブルクリック。

再生位置のx位置は各経路で約79.8%で、`resetViewport`／`followStartUs` の「再生位置から1秒前を基準とした、物理画素丸めを伴う80%追尾」と整合した。約定更新や取得列を混ぜず、リプレイ用の基準を用いて比較した。

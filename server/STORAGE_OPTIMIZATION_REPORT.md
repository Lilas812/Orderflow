## 1. 実施内容

現在の正本・ソース・`GC_IMPLEMENTATION_REPORT.md`を確認し、保存一覧・少数の実ファイルを読み取った。実装・削除・本番書込・再起動・再Publishは行っていない。過去の変更の再適用もしていない。

今回の方針：

- **1秒板は30暦日保持を目標にする。**
- **長期VP集計は残す。**
- **個々の約定を90日保持にするかは未決定。** 365日・無期限とも比較する。
- 期間だけを根拠に未永続化・復旧待ち・限月未確定・集計未検証のデータを削除しない。

結論：

1. GCの実保存データは今回の一覧にない。GC容量をNQと同じと断定できない。
2. NQも完全な取引日の実測値がそろっていない。特に寄り付き中の欠けがあり、単純な時間補正は過小評価になり得る。
3. 現行コードの公開用保存は期限なし。30日・90日の削除はまだ実装されていない。
4. 削除の前に、同じ時間ファイルの再取得・再展開、毎秒の全ファイル一覧／stat、閉じた約定ファイルのgzipメンバー統合を検討する価値がある。
5. 保護中データと無期限の長期集計があるため、保持日数だけから厳密な総容量上限は決まらない。

### 4.4 板30日＋約定90日／365日／無期限＋長期集計無期限

#### 計算方法

各銘柄sについて、稼働開始からの暦日数D、約定保持日数Rとすると、概算は次。

`C_s = B_s(直近30暦日) + T_s(直近min(R,D)暦日) + A_s(全期間) + I_s + H_s`

R＝無期限では`min(R,D)=D`。Iはindex等、Hは期間外でも保護が必要なデータ。実際には旧世代、作業コピー・一時ファイル・48時間キャッシュも別に必要。

**日ごとの実測増分を2時点間で測ってはいない。** 以下は現在の部分データから作る比較用の機械的シナリオであり、必要容量の保証値・採用する予算ではない。

- NQ板：10/28の部分データを時間補正すると約12 MB／稼働日という例になる。全日同じ圧縮率・23時間稼働を仮定。
- NQ約定：上の10/22〜27を各日の取得済み秒数で86,400秒へ比例補正すると約4.26〜9.17 MB／取引日。丸めて4.3〜9.2 MBを例に使う。**寄り付きの欠けがあるため上下限・信頼区間ではなく、実際はこの範囲外にもなり得る。**
- 長期集計：部分4日の時間補正から0.1 MB／取引日を例にする。完全日実測ではない。
- 年間／月間は便宜上5/7を稼働日割合とする。祝日・短縮取引・夏時間を精密に織り込んだ値ではない。板30日は約0.239 GiB、長期集計は年約0.024 GiB増という仮定。

| 長期集計の蓄積年数 | 約定保持 | NQのみのシナリオ GiB | GCも同じ発生量という仮定でのNQ＋GC GiB |
| --- | --- | ---: | ---: |
| 1年 | 90暦日 | 0.521〜0.815 | 1.042〜1.629 |
| 1年 | 365暦日 | 1.308〜2.498 | 2.616〜4.995 |
| 1年 | 無期限 | 1.308〜2.498 | 2.616〜4.995 |
| 5年 | 90暦日 | 0.618〜0.912 | 1.237〜1.823 |
| 5年 | 365暦日 | 1.405〜2.595 | 2.810〜5.189 |
| 5年 | 無期限 | 5.581〜11.530 | 11.163〜23.060 |

表はI・H・旧世代・作業領域を除く。**GC列は実測推定ではなく「GC=NQ」の感度例だけ。** GCの実測後はB・T・Aを別々に置き換える。0.10／0.25というtickSize比で容量を換算してはいけない。GCの任意contractフィールド、価格変動・約定数・圧縮率も異なる。

旧LONGVP_SPECには約定が月約1.5 GBという過去概算も残る。この仮定を使えば、NQだけでも約定90日約4.5 GB、365日約18.25 GBとなり、上の部分データ由来シナリオより大きい。**完全日の確認なしに旧予算を小さい方へ置き換えない。** 旧概算もGCの実測ではない。

#### 設計上限と容量予約

列の最大長は`9 + 8×(400+400) = 6,409 B`。24時間すべてに1秒列がある場合、30日で**16,612,128,000 B＝15.471 GiB／銘柄**、両銘柄30.942 GiBの非圧縮データとなる。gzip後の実測上限ではなく、圧縮に期待しない設計用の基礎値。gzipのオーバーヘッド・境界の時間ファイル・保護延長・一時コピーは別。実際の休場時間はこれより減る。

個別約定には秒あたり件数のアプリ側ハード上限がないため、90日でも厳密な最大B数は日数だけからは出せない。無期限約定、無期限集計、期限外holdにはそもそも有限の累積上限がない。長期日次JSONの約4 MiB制限は拒否条件であり、保存成功する前提の安全な総容量上限ではない。

48時間キャッシュ、書き込み中時間、アップロード用staging、再DL照合用ファイル、原本を残すatomic置換の新旧ファイルが併存する。特に1時間のgzip前板は最大23,072,400 B。必要作業容量は「保存量＋48時間＋書込中＋同時処理の原本／staging／照合分」で別枠にする。固定の空き容量閾値は今回決めていない。

#### 使えなくなるもの・残せるもの

| 保存物の状況 | 保存データだけで残せること | 失う／制限されること |
| --- | --- | --- |
| 直近30日、板と個別約定あり | 現在の保存粒度のヒートマップ再生・約定ベース集計 | 元々1秒板から上流の全L2イベントを完全再現することはできない |
| 31〜90日／365日、板なし・個別約定あり | 約定ベース価格・VP・デルタ等の再計算に必要な元資料 | 過去の板、板由来の大口追跡・glow等を同じ形で再現できない。現UIの範囲表示には種類別の案内が必要 |
| 約定期限より古く、長期集計だけ | 保存済み1分OHLC・売買量／価格出来高、30分×価格集計、そこから作れる既存LONG VP・週VWAP・週CVD等 | 個々の約定、250msバブル、細かいデルタ、任意の分途中の価格別集計、元約定との再照合、集計不具合の精密修復 |
| GC限月不明の集計だけ | 価格調整不要な数量等の参照 | 後から判明した限月境界が集計単位を横切ると、正しい分割を元データなしで復元できない |
| 約定無期限 | 将来の精密再集計の元資料を残せる | 板が30日で消えれば板の再現はできない。容量は年々増える |

現`AppLongVp.build`／`run`は直近7日を対象にする。**約定を365日残すだけで、365日全体の自動再集計機能が現アプリに追加されるわけではない。** 古い生約定は将来の修復に必要な元資料としての価値。履歴APIからの再取得は提供範囲・限月・プラン・欠けに依存し、復元保証に数えない。

UI仕様のPhase 15「1日・1週間」の1分板は案であり、今回の保存済みオブジェクトには見つからない。長期VPだけから板平均を作ることはできない。1秒板の期限後に古い1分板も作り直したいなら、期限前の別集計保存を将来の要件として決める必要がある。今回実装・必須化はしない。

### 4.6 削除を将来検討する場合の保護・coverage整合案

これは設計案であり、今回のコードには追加していない。

1. **保護判定を日数より優先する。** 未アップロード／再DL照合未了、書込中時間、held、応答中pins、復旧用原本・復旧待ち、限月UNKNOWN／境界未確認、必要集計が未検証の元データをholdする。GCのUNKNOWNはgapsなし・complete:trueでも解除しない。NQもcompleteだけで独立照合済みとみなさない。どの種類がその集計に必要かを明示する。
2. 日次保存の成功・SHA一致は転送の検証で、元約定との数量・価格出来高の意味上の検証とは別。検証対象のraw世代／hash、coverage、集計版、contract、件数・買売量・価格出来高、判定結果を記録できることが将来の削除条件。今回の4部分日は安全に削除可能とは判定していない。
3. 暦日cutoffの基準タイムゾーン・当日を含むかは実装前に確定する。取引日・UTC時間ファイル・夏時間を混同しない。イベント時刻の時間ファイル終端がcutoff以前であることを見る。uploadのupdated時刻だけで期限を判定しない。境界をまたぐ時間は安全側で残す。
4. 対象一覧は市場／種類／半開区間／オブジェクト世代／サイズ／保護理由付きでdry-runする。保護量Hは通常保持分と別集計。全GCがUNKNOWNなら、その保護量は期間を超えて増え得る。予算不足でもholdを無断で解除しない。
5. deleteは既存publisherと同じ市場別の状態・キューへ統合する必要がある。別プロセスの期限削除だけでは、古い`this.cloud`や作業coverageが消した範囲を再広告したり、ローカル残骸を再アップロードする危険がある。Objectsへ安全な世代条件付き削除を追加できる経路も別途確認する。
6. 複数オブジェクトの削除とcoverage更新は一括トランザクションではない。**retiringの意図を永続化し読取可能範囲から除外→同じ世代だけ削除→成功分だけcoverageから除外しretention理由を残す**という順序を候補にする。中断時は広告を過少にする側へ倒し、消えたファイルを保存済みと偽らない。失敗・世代変更時は再判定し、データを強制削除しない。
7. cloud coverage、ローカルworking coverage、recordedTicks、bounds、キャッシュ、次回起動の復旧走査を整合させる。retiredを単なる「まだ取っていない」と扱わず、履歴APIによる再取得や自動復旧で復活させない。長期集計・rolls・設定・settings.corrupt原本は別用途として保持する。
8. 現helloの単一savedRangeだけでは、板30日／約定365日／長期無期限の違いを表現できない。種類別の取得可能区間と保持期限理由を返し、板のない昔を「完全ヒートマップ再生可能」と表示しない。保持範囲revisionでブラウザのexpired coverageも失効させる案。既存クライアントにも、存在しない範囲を成功として返さない。
9. AppStoreの48時間キャッシュの期限処理は「確認済み指紋一致・held/pinsなし」のガードを既に持つ。クラウドの永続削除と同じ処理とはみなさない。LocalStoreの既存7日処理も、そのまま保護付きクラウド削除へ流用しない。

`prod/`全体への単純lifecycle削除は推奨しない。長期集計・設定・不明限月・復旧原本を巻き込み、coverageも古いまま残る。バケット設定を確認できていない状態で変更してはならない。

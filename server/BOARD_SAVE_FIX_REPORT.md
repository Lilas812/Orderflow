# 板保存・停止時引き継ぎの修正報告

## 範囲と公開版

- 作業開始時HEAD: `6def822acb1bdce430d00c18093737a4afc77596`。開始時の未コミット差分なし。
- 公開メタデータは private / VM / successful build。commit SHAは含まれず、**公開中のcommitは特定できない**。origin/mainや日時から推定していない。
- Publish、本番書込、稼働受信・サーバーの停止／再起動、実上流接続、依存追加なし。
- App StorageはCLIによる直接の読取だけ。本番アプリHTTP／本番VMでのデコード処理なし。

## 原因の再現と修正

### 1. 書きかけ時間の消失

旧方針は、SIGTERMでローカルをflushしても、進行中のUTC時間はApp Storageへ上げない。ディスクが消失した新プロセスにはその板・約定がなく、履歴補完に依存する。この経路を、通常のclosed-hour-only flushを負の対照として隔離再現した。

11/03 12時、11/04 03時の欠けとは整合するが、**当時の書きかけファイル・公開commitを確認できないため、この経路が当時の全欠けを起こしたとは確定できない**。前回確認した受信停止・切断も独立して残る。

修正:

- `ColumnAggregator.flushObserved()`：停止時に最後の受理済みスナップショットを確定。3秒の経過を待たない。新しい秒や補間列は作らない。
- `Pipeline.stop()`：その列と未保存約定を既存の保存キューへ渡す。最初の板を受けた直後の停止でも新しい履歴ジョブを起動しない。板未受信でL未確定の約定も保存する。
- `AppStore.flush()/closed()/publish()`：既存のローカルflush完了後、停止受付時の書きかけ時間も保存対象とする。板の`.bin`をストリームgzip化し、従来と同じ`.bin.gz`オブジェクト名・形式で保存する。通常運転は完了時間だけの公開を維持。
- 停止時は新しい時間を優先し、各オブジェクト1回だけ試す。既存の全体9秒abort／9.5秒hard exit／10秒上限は延長していない。
- 本体とcoverageの再DL・SHA-256照合は維持。保存に失敗した区間をcloud coverageへ加えない。期限切れ・失敗・保存中に版が変わったものは残りとして報告する。
- `AppStore.hydrate()`：同じ時間への新規追記前に、保存済みの前半を読み戻す。本体アップロードだけ成功しcoverage更新が失敗した孤立オブジェクトも、書込前に存在確認・デコード・復元する。存在確認や復元失敗時は後半だけで上書きしない。
- NQ/GCのprefix・価格・約定の到着順・同内容の別約定・巻き戻る約定時刻は維持。

突然の強制終了、ネットワーク断、期限超過時まで「欠損しない」と保証する変更ではない。保存されなかった実測はローカルに残り、再デプロイでそれも消えた場合は履歴API等での回復に依存する。

### 2. 実板秒の独立した確認

- `store/book-seconds.ts: inspectBookSeconds()`：既存バイナリをヘッダー走査し、実在する秒数と連続区間を返す。1時間3,600要素のビット配列、ストリーム展開で処理する。
- `LocalStore.actualBookSeconds(start,end)`、`AppStore.actualBookSeconds(start,end)`：研究／インジケーター用の明示的な読取関数。未保存の保留列を完全性へ混ぜず、ファイル不存在は0、破損は例外。
- 既存coverageの意味・JSON形式は変更しない。取得済み区間と実板列の存在を区別できる。実板があること自体も配信元の完全性の保証ではない。
- 既存インジケーターの判定を自動的に変更したわけではない。必要な呼出元がこの関数を使用できるようにした。

### 3. 段階別カウンター

`diagnostics/board-stages.ts: BoardStageLogger` を `index.ts` へ接続。

各銘柄について60,000msごとに `board_save_stages` を1行、停止時に最終行を出す。deltaと起動以来totalを併記:

- 板受信、正規化採用、拒否
- 拒否の主理由別件数（1件につき1理由。複数不正がある場合は最初の理由）
- 確定列、確定済み秒として不採用になった板
- ローカルへの新規列書込完了数
- watchdog、切断、再接続

拒否理由は固定集合（invalid_fields / invalid_side / invalid_level / off_tick / duplicate_price / book_order / crossed_book / timestamp_rollback）。任意の外部文字列をカウンターキーにしない。

保存カウンターは**ローカル書込完了**であり、クラウドへの保存成功を偽装しない。App Storageの成功は既存の `app_storage_uploaded`、SHA照合、CLIで別確認する。

接続はNQ/GC共有1本なので接続系カウンターには `connectionScope: shared_upstream` を付け、両銘柄の値を足して2接続と解釈しない。1メッセージごとの新規ログ・タイマー・配列保存は追加していない。

### 4. 時間末尾の64秒

- 64秒の板が本体にあり、cloud索引の範囲だけ古い状態をダミーで作成。CLIが64秒を `actualOutsideCoverage` として検出することを確認。
- 現行HEADには既に、gzip本体が同じでもcoverageが増えたら索引を再公開する条件がある。これを重複実装していない。
- 既存キャッシュからの起動時走査・再公開で、64秒のずれが0秒となり本体バイトが変わらないことを確認。
- 追加修正：`shutdownFiles()`はfingerprintだけで確認済み扱いにせず、cloud coverageがローカル範囲を含むかも確認する。これにより**本体確認済み・索引だけ未反映の停止時失敗が「残り」一覧から消える問題**を防ぐ。
- 当時の64秒が生じた特定の公開版・競合順序までは確定していない。実際の過去ファイルや索引の書換はしていない。

## 仕様との差分・ユーザー決定

正本の「書きかけは停止時に上げない」より、今回の「書きかけも失わず保存・引き継ぐ」を優先することをユーザーが承認。正本の本文は変更していない。停止上限10秒は据え置き。追加のメッセージ形式や推測データはない。

## 週末公開の注意点・原状復帰

1. 公開はユーザーが市場休止中に行う。**最初の切替で止まる旧公開コードには今回の書きかけ保存修正はまだない**。最後の取引時間が完了してApp Storageへ本体・索引とも保存されたことを事前に確認する。今回公開を実行していない。
2. 公開対象commitを記録し、通常のSIGTERM終了を使う。強制killや停止上限の延長はしない。
3. 公開後に両銘柄の `board_save_stages`、受信鮮度、拒否理由、確定数とローカル保存数、`app_storage_uploaded`、失敗・残り一覧を確認する。未反映分が残った場合は「保存済み」と扱わない。
4. 最初のUTC時間境界後にCLIで実秒・索引を確認する。市場休止・配信側無通信は別に扱う。設定GET、LONG VPの60秒更新、HEATMAP、FOOTPRINTの既存機能も確認する。
5. 稼働中の新規修正を取り消す場合は今回の変更コミットをrevertし、テスト後にユーザーが再公開する。作業開始HEADをresetして既存変更を消さない。データ形式は同じで旧版も読めるが、旧版には孤立本体の保護がないため、索引未反映・未アップロードが残ったまま安易に戻さない。
6. 本番データは今回変更していないので、今回作業によるデータ復元操作は不要。過去の欠けを自動修復したとは扱わない。

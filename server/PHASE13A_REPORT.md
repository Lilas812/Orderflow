## 3. 限月の実API調査

### 資料と実応答を分ける

参照：`https://tick-stream.xyz/docs/symbols`、`/docs/rest`、`/docs/historical`。
公式説明は個別限月を指定できず、`400 contract_not_addressable` とする。一方、今回の実APIでは `/v1/history/ticks` に `NQU6`・`NQZ6` を指定した2リクエストはいずれもHTTP 200・0件だった。
**0件を「その限月に取引がなかった」と解釈しない。** 個別限月の履歴を取得できた証拠にはならない。

`GET /v1/symbols` はHTTP 200、トップ項目は `futures / options / note`。先物は54件。
NQの項目一覧は `symbol / name / exchange / contract / contractSince / subscribed / streaming`。

```json
{"symbol":"NQ","name":"E-mini Nasdaq-100","exchange":"CME","contract":"NQZ6","contractSince":"2026-09-14T07:46:50.905071381+00:00","subscribed":true,"streaming":true}
```

取得対象はルートのフロント限月連続系列。現在の限月は分かるが、両限月の同時価格や過去の全限月一覧はこの応答にない。`contractSince:null` を「乗り換えなし」と推定しない。
方法(a) overlapを裏付ける両限月データは得られないので、**方法(b) edgeを採用する計画**。

### 2026年9月の実測

`GET /v1/history/ticks?symbol=NQ&start=1789371710&end=1789372311&limit=5000`
（切替前後約5分）：
HTTP 200、1,285行、`truncated:false`、`history_clamped:false`、`snapshot_until:null`。
応答行は指定半開区間でフィルタし、切替前の最後と切替以降の最初を時刻順に選ぶ。端点外の行は使わない。

| 項目 | 値 |
| --- | --- |
| 直前の約定 | tsUs=1789372010853060、29,215.50、116,862 ticks |
| 直後の約定 | tsUs=1789372010920253、29,215.75、116,863 ticks |
| diffTicks | 116,863 − 116,862 = **+1 tick**（+0.25ポイント） |
| method | `edge` |
| 約定間隔 | **0.067193秒** |

これは仕様(b)の連続系列の境界差であり、同時刻の2限月間スプレッドを測定した値ではない。
旧限月名はAPI応答に含まれず、`NQU6` という名前まで実APIで裏付けられていない。推測した名前で9月分の `rolls.json` を自動登録しない。
今回の初回7日分は9月境界より後で現限月の期間内。9月の数値は本報告に残し、過去の旧限月名を要する登録は根拠を得るまで保留する。
今後は前後の `/symbols` 記録で `from/to/atSec` を保存し、境界両側の保存約定からedgeを計算する。片側不足・未知限月を0差で埋めない。

なお、公式の `/ticks` は7日制限だが、今回の `/history/ticks` は9月分を取得できた。「履歴がすべて7日より前は取れない」とは実測上断定できない。
**今回の取り込み・不足の再試行対象は指示どおり直近7日に限定し、過去へ勝手に拡張しない。** この調査用の9月取得はロール差算出の指定に基づく。

## 4. 承認された実装計画（計画時の記録）

### 4.1 保存切り替え（DBは残す）

1. 長期VPの起動経路をApp Storage版へ変更し、PostgreSQL接続を使わなくする。DB・データ・既存スキーマは削除しない。依存の追加・削除もしない。
2. 既存の `ReplitObjects` と `uploadVerified` を再利用。日次を一時ファイルでgzipし、アップロード後に再ダウンロードしてSHA-256一致を確認する。失敗を状態に出し、再試行する。確認前に完了扱いしない。
3. 日次は正本3.3のversion 1配列形式、rollsは3.5の形式だけを追加する。既存生約定・列・coverageの形式は変えない。
4. 開発の明示有効化の環境変数は未追加。名称案は `LONG_VP_DEV_ENABLE=1`。開発は無効が既定、有効時も書込先を必ずdev/に固定する。既存の開発上流WS禁止は維持する。

### 4.2 約定をそろえる共通処理

1. `VpHistory` の窓処理と `HistoryClient` を再利用できる形に限定的に抽出する。別の履歴取得実装を増やさない。
2. `recordedTickCoverage` で区間を分け、保存済み部分を `visitTrades` で読む。不足部分だけRESTへ進む。
3. 15分以下、limit 500,000、半開区間、truncated時の分割、5分成熟待ち、通信失敗は初回込み3回、直近0件は初回＋再取得3回を維持する。
4. 既存の原子差し込み `replaceTradeRange` を使う。既存行・重複した正当な約定・行順序を保持し、予期しない既存行との衝突は明示的失敗にする。
5. 既存ヒートマップの履歴処理と長期VPを同じ直列化・停止制御で調停する。ライブ優先で譲り、同じ不足を二重取得・二重挿入しない。新しい上流WSは作らない。
6. 1窓が確定してから集計へ反映する。保存更新の途中を同時読みして重複計上しない。先頭が7日制限をまたぐ取引日は未取得範囲をgapsとして残す。

### 4.3 集計・日次・当日

1. `calendar.ts` をCT/ETの壁時計・DSTと正本の帰属に合わせる。UTC固定オフセットは使わない。
2. 1分OHLC/買い/売りと30分×1tick/買い/売りを逐次集計し、限月番号と順序を固定する。空の分を生成しない。価格はすべて整数tickの生価格。
3. 直近7日内の終了済み取引日を1日ずつ処理し、gapsがなければcomplete。起動のたびに全日をREST再取得せず、保存済み日次と不足を確認する。
4. 日次タイマーは終了日の集計と直近7日の不完全日の再構築を行う。悪化した結果で良好な日次を置換しない。7日外のgapsも消さない。
5. 当日は保存約定から復元し、不足だけ補充。その間のライブ受信は同じデータを二重加算しないよう境界・保存確定を管理し、暫定値は常にcomplete:false。日次保存前はメモリ集計だけとする。
6. 今後の限月の変化を `/symbols` で追跡し、切替記録とedgeの根拠を保存する。取得頻度案は起動時と60秒ごと（実装前の承認対象）。変化は `contractSince` の実時刻で適用し、取得時刻へ丸めない。価格差を算出できない場合はHTTP状態に未確認として明示し、偽の0差を永続化しない。

### 4.4 APIとキャッシュ

- `GET /api/longvp/days?from=YYYY-MM-DD&to=YYYY-MM-DD`：日付を検証し、実在する取引日基準で60日まで。保存されていない日を架空の完全データにしない。
- `GET /api/longvp/today`：正本と同じ形、complete:false。60秒ポーリング用。WSの形は変更しない。
- `GET /api/longvp/rolls`：検証できた記録だけ。
- 既存サイトと同じルーティング・アクセス制限下へ追加する。既存ヒートマップのAPI/配信を維持する。
- キャッシュはLRUで日数と推定バイト数を両方制限する。暫定案は8日・32MiBのうち先に到達する上限。1日ずつ読んで60日分を無制限に保持しない。応答処理中のメモリも別途測定し、上限値を最終報告する。
- `/api/status` の長期VP状態は、有効理由・bootstrap進捗・確定日数/範囲・不完全日・ロール件数・次回処理・cache使用量/上限・エラーを示す。配置は新仕様のトップレベル `longVp` とし、既存の `phase2a.longVp` を変える必要性・互換性も実装時に明示する。WS状態は変更しない。

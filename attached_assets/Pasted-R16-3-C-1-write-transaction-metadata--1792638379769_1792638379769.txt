### 2. C-1の実装範囲

- EventJournalのprivate commit処理内だけでVerifiedMetadataViewを生成する。
- verifyMetadataの全検証を維持する。
- checksum、ordered root、全索引列、連続位置、retention証明を維持する。
- 同一connection・同一transaction・同一読み取り世代でのみmetadataを再利用する。
- 元イベントの読み込み・checksum・descriptor照合は省略しない。
- 過去状態の意味的replayも引き続き実行する。
- 最初のINSERTより前にviewを破棄する。
- INSERT後のsaveStorageStateでは従来どおり新世代の索引を読み直す。
- commit間・プロセス間でviewを保持しない。

VerifiedMetadataViewという名称を理由に、原本まで検証済みと扱ってはいけません。

### 3. 世代と所有権の検証

次の条件を必須とします。

- connectionとtransactionの同一性を検証する。
- transaction tokenは使い回さない。
- view生成後に内部DML・DDL・保持処理・migrationなどの変更があった場合は再利用を拒否する。
- total_changes、data_version、schema_version、user_version等を利用する場合、それぞれが検出できる変更と検出できない変更を区別する。
- 特にdata_versionだけで同一connection自身の変更を検出できると仮定しない。
- viewを外部へ公開しない。
- awaitを跨いで保持しない。
- 異常時に未検証metadataを正常なものとして採用しない。

### 4. 読み取り予算

以下の暫定上限をR16.3の有限MOCK検証に限って承認します。

- 同時VerifiedMetadataView：1個
- 最大descriptor数：16,384件
- 最大serialized payload：16MiB

上限到達前に事前検査を行い、超過した場合は明示的なエラーと停止要求を出してください。

ただし、これは将来の本番市場データの保存件数上限ではありません。

既存DBや原本を削除・切り詰めることは禁止します。

公開read/replay APIに新しい上限を無断で適用しないでください。

C-1を利用するprivate書き込み経路で上限に達した場合の挙動、既存挙動との差、今後のbounded reader移行に必要な変更点を報告してください。

上限超過時に無制限の旧方式へ黙ってfallbackすることは禁止します。

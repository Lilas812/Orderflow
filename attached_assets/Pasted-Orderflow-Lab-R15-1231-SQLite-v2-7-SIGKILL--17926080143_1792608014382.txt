## 1. 実装目的

大量の市場イベントを受信する環境を想定し、次の機能を実装します。

- 受信イベントの独立キュー
- バックプレッシャー制御
- キュー容量上限と警告
- イベント欠落の検出
- 保存済みイベント位置の追跡
- 通信切断・自動再接続のMOCK
- Snapshotによる安全な再同期
- 受信・処理・保存のメトリクス
- 処理遅延と描画遅延の計測
- 大量イベントによる性能試験
- Data Statusの状態表示

最も重要な原則は、イベントの完全性を保証できない状態で正常表示を継続しないことです。

## 4. イベント処理パイプライン

次の責務を分離してください。

MOCK Transport
→ Event Validation
→ Sequence / Quality Check
→ Audit / Durable Storage
→ Canonical State
→ Derived Data
→ Renderer

要件：

- イベント受信と描画を分離する。
- 受信イベントをReact stateへ直接大量投入しない。
- 保存可能なイベントを順序どおり処理する。
- 受信順とexchangeTimeNsを区別する。
- 保存・適用の成功位置を追跡する。
- 画面更新は原則250ms間隔。
- 描画更新を間引いても市場イベントを捨てない。
- UIが遅れても保存処理を継続できる設計にする。

本格的なサービス分離が追加承認なしでは実装できない場合は、計算ロジックとMOCK検証を先行し、実プロセス連携は保留してください。

## 5. バックプレッシャー

イベントキューに容量上限を設けてください。

上限値は決め打ちせず、推奨値・メモリ使用量・理由を最初に報告してください。

キュー容量を超えそうな場合：

- 上流が停止可能なら受信を一時停止する。
- 停止できなければ品質障害を明示する。
- 欠落が発生した場合は該当scope・channelを無効化する。
- L2で欠落が起きたら古い板を正常な現在板として表示しない。
- 保存失敗を無視して正常動作を装わない。

単に配列の古い要素を削除する方式は禁止します。

キューの最大深度、滞留時間、溢れた件数を測定できるようにしてください。

## 6. 計測するメトリクス

少なくとも以下を記録してください。

- receivedEvents
- acceptedEvents
- appliedEvents
- persistedEvents
- duplicateEvents
- rejectedEvents
- queueDepth
- peakQueueDepth
- storageFlushLagMs
- eventProcessingLatencyMs
- latestExchangeEventTime
- latestPersistedEventTime
- latestRenderedEventTime
- renderLagMs
- sequenceGapCount
- reconnectCount
- storageErrorCount

件数には「受信した配信数」「重複除去後の論理イベント数」「保存済み監査記録数」を区別する定義を持たせてください。

received = applied = persisted と単純に仮定してはいけません。

各ステージの保存・処理位置を使って、説明可能な件数整合性を確認してください。

保存が失敗したらpersistedを増やしてはいけません。

メトリクスは実測値と、測定不可能な値を明確に区別してください。

## 7. 自動再接続MOCK

通信切断を模擬するControllerを実装してください。

暫定的な再試行間隔：

1秒 → 2秒 → 4秒 → 8秒 → 16秒 → 最大30秒

ジッターを加える場合は、テスト用に決定的な時計と乱数を注入できる構造にしてください。

重要：

- 通信が再接続しただけでL2をVALIDへ戻さない。
- 新しい正常Snapshotと必要なsequence整合性が確認された場合だけVALIDへ復帰する。
- GAP中の古い板を現在値として公開しない。
- L1、L2、TRADESの品質を独立して管理する。
- 既存のR03品質管理を再利用する。

外部通信APIへの実際の接続処理は今回実装しないでください。

## 8. 負荷試験

決定的なMOCKイベント生成器を用意してください。

試験負荷：

LOW：1,000 events/s
MEDIUM：10,000 events/s
SPIKE：50,000 events/s

これらは実際のNQのイベント発生レートではなく、検証用の試験値です。

各試験で以下を測定してください。

- 投入件数
- 受信件数
- 重複件数
- 適用件数
- commit済み件数
- 明示的な欠落件数
- キュー最大深度
- 平均処理遅延
- p95 / p99処理遅延
- SQLite/チャンク書き込み速度
- WALサイズ
- メモリ使用量
- CPU使用率
- ディスク容量増加
- 範囲読込時間

実際に維持できた処理速度と、要求した投入速度を別々に報告してください。

測定していない性能を達成済みと記載してはいけません。

Replit環境で50,000 events/sを維持できない場合は、失敗条件、実測限界、ボトルネックを報告してください。

保護機能を解除したり、無制限に負荷をかけたりしないでください。

長時間試験は短時間試験で安全性を確認した後に実施し、環境制約で完了できなければ未実施と明記してください。

## 10. 障害注入

次のケースを検証してください。

A. Sequence GAP
- L2のseq10→12
- L2をGAPへ変更
- Tradeが正常なら独立して維持

B. 通信切断
- MOCK受信停止
- RECONNECTING表示
- 再接続のみではVALIDに復帰しない

C. 保存失敗
- ディスク書き込みエラーを注入
- STORAGE ERROR表示
- 未保存データを保存済みと偽らない

D. キュー超過
- 容量上限を超える負荷
- 無言のイベント破棄を禁止
- 保証できないscopeを無効化

E. 遅延処理
- 保存・計算・描画へ意図的に遅延を注入
- 最新モデル時刻と描画時刻を区別

F. プロセス停止
- 保存済み位置を記録
- SIGKILL後に復元
- 未commitデータを正常保存済みとして扱わない

G. WebGL context lost
- 表示障害をデータ保存障害と混同しない
- 描画復旧後も数量・Deltaを維持

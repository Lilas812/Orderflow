# 本番の保守の手順

## 今回の境界

**これは手順書。公開停止、購入データの本番反映、Publish、本番の再起動は実行していない。**
実施順序はユーザー指定どおり、次の1回の保守にまとめる。

1. ユーザーが公開を止める。
2. 購入データの42日分を反映し、照合する。
3. 修正版をユーザーが再Publishする。
4. 起動後に日次処理と履歴取り込みを確認する。

開発で通ったダミー試験を、実クラウド・本番で動いた証拠と取り違えない。
日次停滞の過去ログ調査は `LONGVP_DAILY_DIAGNOSIS.md`、
購入データの既存候補と制限は `LONGVP_PROMOTION_TOOL_REPORT.md` を参照。

## 停止前の準備（ここを終えてから停止する）

- 購入データ反映の担当作業で、**対象42日分の一覧を銘柄・取引日・限月・UTC半開区間付きで確定**する。
  NQとGCの延べ日数か、異なる日付の数かも一覧に明記する。今回の修正では42日の採用・反映を行っていない。
- 42日すべてについて原約定、coverage、LONG VPの日次集計の対象と数量が整合した、検証済みパッケージを作る。
  GCの不明方向は不明のまま、未確定の限月を現期近に推測割当しない。
  原約定とcoverageなしに、日次の合計だけを多い値で置換しない。
- **既存のprepare-longvp-promotion CLIは候補作成専用で、--apply/--uploadは拒否する。**
  本番writer・42日の全採用・反映前後の照合手段が揃っていない状態で、先に公開を止めない。
  今回追加したのは稼働版の日次writerの世代条件であり、購入データ全体の投入CLIではない。
- 停止中に実行する反映コマンド、検証コマンド、対象一覧、戻しコマンドを実際のパッケージに合わせて記録する。
  書込先はprodであることを二重確認し、隔離dev試験と読み取り専用の事前スナップショットで手順をリハーサルする。
- 修正版の型検査・試験・ビルドを通す。対象のソース状態と依存lockを固定する。
  ステップ2の最中に修正版や旧版が自動起動しないよう、公開の稼働停止を確認する。
- 本番停止中の書き手は反映作業だけにする。開発の上流WSを有効にしない。
- 原本を復元できる別保存先と世代・SHA-256の一覧を用意する。
  設定、原約定、coverage、日次、rollsを対象にし、秘密値をログや手順書へ出さない。
- 可能なら市場休止中・週末に実施する。CT/JSTの変換は当日の夏時間で再確認する。

## 停止時間の見込み

**事前準備・42日パッケージの作成を除いて、受信再開まで60〜90分を仮の保守枠とする。**
42日実反映の計測値はまだなく、保証値ではない。リハーサルの実測で停止前に見直す。

| 停止中の工程 | 仮の枠 |
|---|---:|
| 停止確認、最終の読取バックアップと世代照合 | 5〜10分 |
| 42日パッケージ反映と再ダウンロード照合 | 30〜50分 |
| 再Publish、保存復元・起動・両銘柄の受信再開 | 10〜20分 |
| 初動の履歴・日次確認 | 約10分 |

履歴の全欠けが埋まり終わるまでの時間は、この停止時間とは別。
ライブ受信再開後も取り込みは並行して続き、上流の遅延・1分窓の再試行で数時間になることがある。
分割の最小窓でも通信3回失敗すればgapとなるため、回収完了時刻を約束しない。

**作業上限は停止から受信再開まで2時間未満。**
既存の板の初回履歴は、起動後の最初の確定ライブ列を基点に直近3時間のみ。
公開停止時刻だけでなく、停止前の最終保存時刻から再開後のseamまでが3時間未満になる必要がある。
1時間程度の余裕を残し、反映・起動が間に合わない見込みなら、検証済みの戻し手順で受信再開を優先する。
2時間を超えそうになってから手順を考えない。長期VPの7日範囲だけを根拠に、板の全停止区間が戻ると説明しない。

## 1. ユーザーが公開を止める

1. 停止直前のNQ/GCの最終受信時刻、保存済み範囲、日次一覧・世代・ハッシュを採取する。
2. ユーザーがPublishingから公開を停止する。担当者は勝手に停止・Publishしない。
3. 稼働プロセス・上流受信が止まり、旧writerが残っていないことを確認する。
   ブラウザを閉じたこと、HTTPが一時的に応答しないことだけを停止の証拠にしない。
4. 停止時刻T0と最後の保存確認時刻をUTCで記録。
   通常終了にはアップロードを含む約9秒の予算があるが、強制終了時の未永続分まで保存できたと仮定しない。
5. 停止後の最終バックアップ・世代を採取し、事前パッケージの前提と比較する。
   変化していたら新しい元データで再照合する。古いスナップショットで上書きしない。

## 2. 購入データ42日分を反映し、照合する

1. 対象一覧42件とパッケージのハッシュを確認し、1日ずつ検証済みwriterで反映する。
2. 既存の対象オブジェクトは世代条件付きで更新する。新規作成はifGenerationMatch=0。
   競合したら停止して最新を読み直し、既存区間・既存行を保全して判定し直す。無条件上書きに切り替えない。
3. 元の約定行・限月・時刻・買い/売り/不明数量を保ったまま、不足区間だけ補う。
   既存行の重複採用・削除・並べ替えや、coverageだけの完全扱いをしない。
4. 各日のクラウド成果物を再ダウンロードし、gzip/JSONの検証、サイズ・ハッシュ、半開区間、
   買い/売り/不明別の価格別数量、1分足、30分VP、限月、coverageとgapsを独立に照合する。
5. 42日の一覧に「反映前世代/ハッシュ」「反映後世代/ハッシュ」「検証結果」「残るgap」を記録する。
   対象外の既存ファイルが変わっていないことも確認する。
6. 42日すべて合格してからステップ3へ進む。未反映・保留日を完了に含めない。
   不一致や期限超過時は、反映前のバイト列を現在世代への条件付きで復元し、再ダウンロード照合してから旧版再開を判断する。

## 3. ユーザーが修正版を再Publishする

1. 反映の検証記録を確定し、書き手を止めたままユーザーへ結果を提示する。
2. ユーザーが、固定した修正ソースとlockを再Publishする。
   開発プレビューの再起動を本番への反映と取り違えない。
3. 公開buildの成功と、対象版が実際に稼働したことを起動ログ・新しい日次ログで確認する。
4. 保存済みファイル・coverage・日次の復元が済んだ後、
   両銘柄の購読、最初の確定ライブ列、`live_history_seam`をそれぞれ確認する。
5. 受信再開T1を記録し、最終保存時刻から各銘柄のseamまでが履歴取得範囲内かを確認する。
   GCだけseamが出ない等のときは、NQの成功で代用しない。

## 4. 起動後の日次処理と取り込みを確認する

### 止めている間に受信できない分の回収

- T0〜T1はライブでは受信できない。起動後、各銘柄の最初の確定列を基点に、
  既存の履歴取り込みが**直近3時間の板・約定の未取得区間をRESTで取り直す**。
- LONG VPは別途、直近7暦日の不足約定を保存済みcoverageに基づいて回収・再構築する。
  42日の購入履歴の古い日を、この7日回収で取り直せるとは扱わない。
- 保存済み区間は再利用し、補完対象の既存行を消さない。
  直近5分の未成熟区間は待ってから取得し、ライブ/履歴の境界は半開区間で分ける。
- `network_or_timeout`は大きい窓を同じ大きさで3回待たず、1分以上の子窓へ分割。
  元から1分未満の不足は広げず、その区間を処理する。
  1分（またはそれ以上を合法に二分できない短い端数窓）で3回失敗したらgapとして次へ進む。
- 従って、停止区間は取得可能範囲なら起動後に自動で履歴再取得される。
  ただし上流にデータがない・上流障害が続く・起動後のseamが出ない・範囲外のときに完全回収を保証しない。
  「取得要求を出した」と「保存・照合が完了した」を分け、取れない分は欠けとして報告する。

### 日次保存

- 起動時にも保存済み約定だけを使う日次checkpointが動き、履歴の長時間待ちから独立する。
- NQの限月は確認できた期間だけに割り当てる。保存済み日次の最終限月を将来へ延長しない。
  metadata未取得・最終観測時刻より後等の未確認区間は、原約定を保ったままgapとし、誤った限月の行を作らない。
  最初のmetadata確認・限月切替・取引日末を越えた確認後は、次のtimerでもcheckpointを取り直せる。
- **CT16:55**には記録済み範囲で当日ファイルを保存する。
  取引日末CT17:00までの残りはgapなのでcomplete=false。タイマーは60秒間隔のため開始に最大約1分の差がある。
- 取引日の帰属は従来のCT17:00〜翌17:00を維持する。早いcheckpointで末尾の5分を捨てない。
- **CT17:05以降**にもcheckpointを取り直す。履歴補完側も直近7日の不完全日を再構築し、良くなれば保存する。
  CT17:05になっただけでは完全扱いしない。gapsが残ればcomplete=false。
  CT17:00〜17:05に起動・再確認した場合も、末尾の未成熟区間をgapとし早期にcompleteにしない。
- `long_vp_run_*`、`long_vp_stage_*`、`long_vp_day_saved/preserved`を銘柄別・runId別に確認する。
  recorded_onlyと履歴補完側を区別し、backfill/VPがrunningのままでもcheckpoint保存が進むことを確認。
- 各日次uploadは最新世代を読む。条件競合後は最新本文でimprovesDayを再評価し、
  外部から反映した購入分を失う候補ならpreserveする。5回連続競合はエラーで止め、強制上書きしない。
- 新しい日次の世代・本文・件数・gapをread-onlyで取り直し、42日反映分が維持されていることを確認する。
- GCの`long_vp_failed`には例外name/message/stack/causeが出る。秘密値は既存loggerで伏せる。
  失敗が消えたことだけでなく、日次save/preserveと後続窓への進行を確認する。

### 合格・終了

1. NQ/GCのライブ受信が継続している。
2. 停止前最終保存〜各seamの板・約定のcoverageを照合。未取得区間があれば理由と再回収可否を列挙。
3. 42日反映分の照合記録が全件合格し、起動後のwriterが減量・欠損拡大していない。
4. 履歴の分割・1分窓再試行・欠けの記録がログと保存結果で一致している。
5. 日次checkpointが先行履歴待ちに止められず、取れた範囲と欠けを正しく保存する。
   時間帯が違う場合、CT16:55と17:05の実運用確認はその時刻まで受信を止めずに継続観測する。
6. 確認で開いたブラウザ・補助接続だけを閉じ、終了を確認する。稼働受信プロセスやユーザーの既存ブラウザは止めない。

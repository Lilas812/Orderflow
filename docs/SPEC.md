## 3. 全体構成【確定】

```
TICK STREAM ──(WebSocket 1本: 約定・板)──▶ サーバー（Node.js + TS, 1プロセス）
            ──(REST: 過去の約定・板)────▶   ├ upstream    接続・再接続・死活監視
                                           ├ ingest      受信・正規化・検査
                                           ├ book        板の状態管理（全量置き換え）
                                           ├ aggregate   ヒートマップ列・集計・間引き
                                           ├ history     REST から過去の板・約定を取得し、列を作る
                                           ├ store       集計した列と約定の保存（App Storage）
                                           └ hub         ブラウザへの配信（WebSocket）
                                                 │
                                                 ▼
                                   ブラウザ（Safari / iPad / iPhone）
```

- TICK STREAM への WebSocket 接続はサーバーから1本だけ。ブラウザが何台つながっても増やさない。
- ブラウザは TICK STREAM に直接つながない。APIキーはサーバーだけが持つ。
- ライブの板と過去の板は、同じ集計処理（aggregate）を通してヒートマップの列にする。

## 5. TICK STREAM のデータ（Phase 0 で確定）

根拠は `docs/PHASE0_REPORT.md`（2026-10-25 と 2026-10-26 の測定）。

### 5.1 接続

- WebSocket：`wss://stream.tick-stream.xyz/v1/stream?key=…&symbols=NQ`。約定は URL の `symbols` で、板は同じ接続で `{"op":"subscribe","channel":"book","symbols":["NQ"]}` を送って購読する。
- 全フレームに `type` がある（約定も含む）。`welcome`、`book`、`tick`、`ping`、`feed`、`warning`、`error` がある。
- サーバーは15秒ごとに `{"type":"ping"}` を送る。`{"op":"pong"}` で応答する。45秒応答がないと切断される。
- 接続数の上限：L2 プランで3本。切れたソケットは最大45秒枠を占有する。超えるとコード 4029。
- 銘柄はルート指定（NQ）で、期近への乗り換えは自動。
- こちらから close(1000) を送り、応答を待っても、正常な close が返らず 1006 になる（再現あり）。原因は特定できていない（サーバー・中間経路・Node のクライアントのどこで正常な close が失われたかは不明）。5分の測定中、予期しない切断はなかった。原因を調べ続けるかわりに、5.5 と 8.1 のとおり再接続で吸収し、件数を見張る。

### 5.2 ライブの約定（`tick`）

- 項目：`type`, `symbol`, `price`, `size`, `side`（アグレッサー側 `buy`/`sell`）, `exch`, `ts`。
- `ts` は Unix 秒（10桁）。秒精度しかない。受信時刻との差は 0.12〜1.11秒（秒への切り捨てを含む）。
- 頻度（日本時間 19:20〜19:25 の5分）：平均 1.86件/秒、1秒あたり最大25件。米国の寄り付きはもっと多い。

### 5.3 ライブの板（`book`）

- 毎回、全量のスナップショットが届く。差分ではない。
- 項目：`type`, `symbol`, `bids`, `asks`, `imbalance`, `ts`。`bids` / `asks` は `[price, size]` の配列で、最良価格から順に並ぶ。
- 段数は両側とも400段（1,022件すべて）。段は「注文のある価格」だけで、価格は連続しない（注文のない価格は飛ばされる）。
- `ts` は Unix 秒。同じ `ts` で最大5回届く。
- 頻度：平均 3.4件/秒、1秒あたり最大4件。公式の上限はおよそ7回/秒。
- 整合性：並び順の違反、価格の重複、買い≥売りの交差、ティック外の価格、サイズ0・負数は、1,022件で0件。
- `imbalance` は最良の買い気配・売り気配の枚数だけから計算した `(bestBidSize - bestAskSize) / (bestBidSize + bestAskSize)` と全件一致した。板全体の偏りではないので、アプリでは使わない。
- データ量：WebSocket 全体で約 144MB/時（非圧縮、5分からの換算）。Replit の受信は課金されない。

### 5.4 REST

- ベース URL：`https://api.tick-stream.xyz/v1`、`Authorization: Bearer <key>`。
- 範囲指定の `start` / `end` は Unix 秒。応答には `end` の秒の端数（`end` 秒＋0.9秒前後）まで含まれる。
- `GET /v1/ticks`（symbol, start, end）：直近の約定。start なしだと1時間分のみ。7日前まで遡れる。行の `ts` はマイクロ秒。
- `GET /v1/history/ticks`（symbol, start, end, limit）：NQ の過去約定。行の `ts` はマイクロ秒。
- `GET /v1/history/book`（symbol, start, end, limit）：NQ の過去の板。
  - 1行が1つの価格段。項目は `ts`（マイクロ秒）, `side`（bid/ask）, `level`（1〜400）, `price`, `size`, `flag`。
  - 2026年6月中旬以降は、およそ250ミリ秒ごとのスナップショット。それより前は `flag` 付きの差分形式で、形式が違う。
  - 通常は同じ `ts` に800行（400段×両側）。まれに同じ `ts` に1,600行・2,400行ある。Phase 0 の13件は前後が同じ内容だったが、Phase 2a の3時間では違う内容の組も22件あった（扱いは 5.5）。
  - 1分あたり約17万行、取得に約2.5〜5秒。
- `limit` は 500000 を使う。`limit=500001` も受理されたが、公式の上限は500,000なので変えない。
- 秒単位の `start` で次のページを取ると、同じページに戻って先に進まない。秒単位のページ送りは使わない。
- レート制限（429）は未観測。

### 5.5 運用で見張ること

Phase 0 で原因や意味が分からなかったものは、次のルールで扱い、件数を状態ページとログに出す。【確定】

| 事象 | 扱い |
| --- | --- |
| 板のサイズ0（または負数）の段 | 受信処理で捨てる。件数を数える |
| 板の交差（最良買い ≥ 最良売り）、並び順の違反、価格の重複 | その板は使わず、直前の板を保つ。件数と実例（最初の数件）をログに出す。交差は寄り付き直後の35分で約8,300件中3件あった（Phase 1） |
| 履歴で同じ `ts` に 800行×N回（N ≥ 2） | 800行ずつの組に分け、各組が両側 level 1〜400 そろっているか確かめる。そろっていれば最後の組を使う（列の値を「区間の終わり」にしたのと同じ考え方）。全組が同じか、違う組があるかで件数を分けて数え、実例を残す。800の倍数でない、または組がそろっていない場合は、その時刻の板を使わず件数を数える。Phase 2a の3時間では、1,600行が73組（同じ51・違う22）、2,400行が2組あった |
| 板の `ts` の巻き戻り（前の値より小さい） | その板は使わず、件数を数える |
| 約定の `ts` の巻き戻り | 約定は捨てない。受け取った順のまま使い、件数を数える。履歴では1〜32マイクロ秒の前後が3時間で7件あった（Phase 2a） |
| 1006 などの切断 | 自分で閉じたとき以外は、コードに関係なく再接続する（8.1） |
| `warning`（`ticks_lagged` など）、`feed`、`error` | 捨てずにログに出し、件数を数える。`ticks_lagged` は欠けた区間を記録する（埋めるのは Phase 2 以降） |

## 6. 内部データ表現【確定】

境界（受信処理）で必ずこの形に変換し、以降は外部形式を使わない。

```ts
type TimeUs = number;      // Unix エポックからのマイクロ秒（整数）
type PriceTicks = number;  // 価格 ÷ ティックサイズの整数（NQ は 0.25）

interface Trade {
  tsUs: TimeUs;         // 取引所時刻。ライブは秒精度（秒×1,000,000）、履歴はマイクロ秒精度
  recvUs: TimeUs;       // サーバー受信時刻。履歴から作ったものは tsUs と同じ値にする
  seq: number;          // サーバー内の受信順の通し番号（同じ秒の約定の順序を保つため）
  price: PriceTicks;
  size: number;
  side: 'buy' | 'sell'; // アグレッサー側
}

interface BookLevel { price: PriceTicks; size: number; }

// 板は毎回全量。受け取るたびに丸ごと置き換え、差分の適用はしない
interface BookSnapshot {
  tsUs: TimeUs;         // 取引所時刻。ライブは秒精度、履歴はマイクロ秒精度
  recvUs: TimeUs;       // サーバー受信時刻。履歴から作ったものは tsUs と同じ値にする
  source: 'live' | 'history';
  bids: BookLevel[];    // 最良価格から順。サイズ0以下は除いたもの
  asks: BookLevel[];
}
```

- 時刻の単位変換は受信処理の1か所だけで行う。ライブの `ts`（板・約定とも秒）は ×1,000,000、履歴の `ts` はそのまま使う。桁数から単位を推測しない。
- 価格の整数化も受信処理の1か所だけで行う。整数にならない価格は、そのメッセージごと捨てて件数を数える。
- 受信時刻は `Date.now() * 1000`（分解能はミリ秒）。
- 履歴の板は、同じ `ts` の行を集めて1つの `BookSnapshot` に組み立てる（800行×N回の扱いは 5.5）。
- 2026年6月中旬より前の差分形式の履歴は扱わない。【確定】
- 約定は内容だけで重複を消さない。同じ時刻・価格・枚数・方向の別の約定がありうるため。【確定】

## 7. ヒートマップの集計

- ヒートマップは「時間の区切り（列）× 価格」のマスに、板の枚数を持つ。【確定】
- 列の区切りは、ライブも履歴も取引所時刻（`tsUs`）で決める。ライブの板の時刻は秒精度なので、列の幅は1秒の整数倍に限る。【確定】
  - 理由：ライブと履歴で同じ基準にすると、つなぎ目がずれない。受信時刻で区切ると、ライブだけ0.1〜1秒ずれる。
- 列の幅：1秒。【確定】（2026-10-26 ユーザー決定）
- 1列の値：区間の終わりの時点の板。秒 S の列は、`S×1,000,000 ≤ tsUs < (S+1)×1,000,000` の板のうち最後のもの。ライブで同じ `ts` の板が複数あるときは、最後に受信したもの。【確定】（2026-10-26 ユーザー決定）
- 列は、その秒の板の買い・売りの各段（価格と枚数）をそのまま持つ。丸めは保存時にはせず、描画時に行う。【確定】
- 板が1件も届かなかった秒は、列を作らない。前の列で埋めない（欠けとして扱う）。【確定】
  - Phase 2a の3時間では、こうした1秒の欠けが8か所あった（捨てた板と、板が来なかった秒）。
  - 描画では、2秒以下の欠けだけ直前の列を表示に使う。保存データは埋めない。3秒以上の欠けは背景色のまま。【確定】（2026-10-27 ユーザー決定）
- ライブの列の確定：秒 S より後の `ts` の板が届いた時点で、S の列を確定する。届かないまま、受信時刻で S+3秒を過ぎたら、その時点で確定する。【確定】
- 1秒の列に入る板の回数は、ライブがおよそ3〜4回、履歴がおよそ4回でほぼ同じなので、ライブと過去の見た目の差は小さい。
- 板は400段ぶんしかないので、最良気配から離れた価格は「注文がない」のではなく「分からない」。描画では両方とも背景色でよいが、大口板の継続時間を数えるときは、400段の外に出た板を「消えた」と扱わない。【確定】
- 価格の丸め：ティック幅で丸める（参考記事の方式）。丸め幅は設定画面に入れない（2026-10-28）。【確定】
- 色のスケール：上限と下限の2つの閾値と、コントラストで決める（Bookmap の upper / lower cutoff と同じ考え方）。【確定】（2026-10-28 ユーザー決定。それまでは上位％の上限だけ）
  - **上限 U**：この枚数以上は最大色のまま。決め方は2つ（設定 `heatUpperMode`）。
    - 自動（初期値）：画面に見えている範囲の、注文のある価格のマス（枚数1以上）の枚数のうち、上位 `heatTopPct`%（初期値1%）にあたる値。0枚のマス、欠け、400段の外は計算に含めない（含めると、板がまばらな時間ほど基準が下がって全体が飽和するため）。
    - 枚数で指定：`heatUpperSize` 枚で固定。相場が変わっても色の意味が変わらない。
  - **下限 Lo**：この枚数以下のマスは塗らない（背景の黒のまま）。小さい板を消して、厚い板だけを浮かび上がらせるため。決め方は3つ（設定 `heatLowerMode`）。
    - なし（初期値）：Lo = 0。
    - 下位％：上限の自動と同じ対象のマスの枚数のうち、下位 `heatLowerPct`% にあたる値。
    - 枚数で指定：`heatLowerSize` 枚。
  - Lo が U 以上になったときは、Lo を U − 1 にする（全部が消えないようにする）。debug 表示に「下限を上限の手前に合わせた」と出す。
  - 色の位置：`t = min(max((枚数 − Lo) ÷ (U − Lo), 0), 1)`、`t' = t ^ heatGamma` を色の段階（UI_SPEC 4）に当てる。`heatGamma` は1（初期値）で直線。1より小さいと小さい板が明るく、1より大きいと大きい板だけが目立つ。
  - 基準の値（自動の上限、下位％の下限）は、表示範囲が変わったときと、新しい列が来たときに計算し直す。ただし計算は1秒に1回までにし、急に色が変わりすぎないようにする。
  - 今の板の色の帯（7.2）も、同じ U・Lo・コントラストで塗る。
  - 現在の板の棒の長さは上限 U だけを使う（下限とコントラストは使わない）。
  - ヒートマップ左上の表示に、今の U と Lo の値と決め方を出す（例「上限 19（上位1%）／下限 なし」）。
- 拡大縮小で1画素に複数のマスが入るとき（時間方向・価格方向とも）は、その中の最大の枚数を使う。大きな板が縮小で消えないようにするため。【案】

### 7.1 約定の集計（バブル・価格ライン・VP・デルタで共通）【確定】（2026-10-27 ユーザー決定）

- 約定は「秒 × 価格（1ティック）」ごとに、買い（アグレッサーが買い）と売りの枚数を合計して持つ。秒は取引所時刻の秒（ライブは `ts` の秒、履歴はマイクロ秒を秒に切り捨て）。
- この集計は、約定バブル（Phase 4）、VP（Phase 7）、デルタヒストグラム（Phase 8）で共通に使う。画面側の独立した部品として作る。
- ライブの約定（`trades`）と範囲の約定（`rangeTrades`）を同じ集計に入れる。内容で重複を消さない（6 節）。範囲の約定を取り直したときは、その範囲の集計を作り直す。
- 手元に持つ約定の範囲：ライブ受信中は、最新に受信した約定まで持つ。画面が追いかけ中か、過去へスクロール中かには関係なく持つ。古いほうは2時間で捨てる。リプレイでは再生位置までの約定だけを持つ。【確定】（2026-10-28）
  - 以前は「最新の確定列＋1秒未満」で切っていたため、確定前の今の秒の約定が集計に入る前に捨てられていた（Phase 4 からの不具合。Phase 8 で直した）。

**約定バブル（Phase 4）**

バブルの作り方は、DeepCharts の Volume Bubbles を参考に、設定で選べる（2026-10-28 ユーザー決定、Phase 11）。初期値は Phase 4 からの動き（1秒×1ティック、出来高、平方根、多いほうの色）のまま。

- **まとめ方**：約定の集計（秒×1ティック）を、時間 `bubbleTimeGroup` 秒 × 価格 `bubbleTickGroup` ティックの区間に合計してから、バブルを作る。【確定】
  - 時間：`1`（初期値）・`5`・`15`・`60`・`auto`。`auto` はデルタヒストグラムの今の1本の秒数（7.5）と同じにする。区切りは取引所時刻で、秒数の倍数に合わせる。ライブの約定の時刻は秒までしかないので、1秒より細かくはまとめられない。
  - 価格：`1`（初期値）〜`20` ティックの整数、または `auto`。区切りは「価格ティック ÷ N の切り捨て × N」。`auto` は 1・2・4・8・16 ティックのうち、1つの区間の高さが 4 CSS px 以上になる最小のもの。
  - 位置：その区間の時間の中央、価格の中央。
- **表示の種類** `bubbleMode`：【確定】
  - `volume`（出来高、初期値）：値＝買い＋売り。
  - `delta`（デルタ）：値＝|買い − 売り|。色は買いが多ければ緑、売りが多ければ紫。
  - `split`（売買分割）：1つの円を縦に半分に分け、左半分を売り（紫）、右半分を買い（緑）にする。それぞれの半円の半径は、その側の枚数から求める。閾値の判定は買い＋売りで行う。
- **閾値** `bubbleMin`：区間の値（表示の種類の値）が閾値以上ならバブルを出す。初期値10枚。
- **大きさの伸び方** `bubbleScaleMode`：値 v、閾値 th、倍率 s（`bubbleScale`）として、半径は次のとおり。どれも上限 `14 × s` CSS px。【確定】
  - `sqrt`（平方根、初期値）：`3 × s × √(v ÷ th)`（面積が枚数に比例）
  - `linear`（直線）：`3 × s × (v ÷ th)`
  - `log`（対数）：`3 × s × (1 + ln(v ÷ th))`
  - `split` の半円は、その側の枚数を v として同じ式で求める（閾値を下回る側も描く。半径の下限は 1 CSS px）。
- **色の付け方** `bubbleColorMode`（`volume` のときだけ）：【確定】
  - `majority`（多いほうの色、初期値）：買いが多ければ緑、売りが多ければ紫、同じなら灰。
  - `ratio`（割合）：`(買い − 売り) ÷ (買い＋売り)` が −1 で紫、0 で灰、+1 で緑になるよう、色をなめらかに混ぜる。縁の色も同じ割合で混ぜる。
- **不透明度** `bubbleOpacity`：塗りの不透明度。初期値0.8。縁は今までどおり。【確定】
- 縮小して1画素の幅に複数の区間が入るときは、同じ画素の幅・同じ価格の区間のバブルを1つにまとめて描く（値を合計し、色は合計後の買いと売りで決める）。閾値はまとめ方の区間で判定したあとにまとめる。

**価格ライン（Phase 4）**

- 各秒の最後の約定価格（同じ秒の中は受信順で最後）を結ぶ線。約定のない秒は、直前の価格のまま横に伸ばす。
- 縮小して1画素の幅に複数の秒が入るときは、その画素の範囲の最高値と最安値を縦線で結び、画素どうしは最後の価格でつなぐ。【案】
- 描く順番：ヒートマップ → 現在の板（7.2）→ 価格ライン → 約定バブル → 現在値の点線。

**Phase 4 で決めた細かい値**【確定】（2026-10-27、Phase 4 の実装時に指定）

- 現在値の点線：白 `#ffffff`、太さ1 CSS px、4px の線と4px の隙間。
- バブルの縁：塗りを約40%暗くした色（買い `#2a9a5c`、売り `#7436b3`、同数 `#989898`）、太さ1 CSS px。
- バブルの半径：上の「大きさの伸び方」（初期値の `sqrt` では `min(14 × s, 3 × s × √(合計枚数 ÷ 閾値))` CSS px）。
- `bubbleMin` が不正（整数でない、1未満、数字でない）なら無視して10を使い、debug 表示に「bubbleMin 無効」と出す。上限は設けない。
- 価格ラインは、最初の既知の約定価格より前は描かない。

**現在値（Phase 4）**

- 現在値は最新の約定の価格。リプレイ中は、再生している時刻までの最新の約定の価格。
- 白い点線の水平線を、ヒートマップ本体の幅（今の板の棒の部分を含む）に引く。価格軸の列には、その高さに現在値のラベルを出す（UI_SPEC 3.10）。
- 過去へスクロールして追いかけを止めているときも、現在値の点線とラベルは最新の値で出す。

### 7.2 現在の板（Phase 5、2026-10-27 に置き方を変更）【確定】

- 最新の板（kind 3）の各段を、横棒（横向きのヒストグラム）で描く。独立した枠にはせず、ヒートマップ本体の右端から左へ伸ばし、ヒートマップの上に半透明で重ねる。不透明度は設定 `bookBarOpacity`（初期値0.5）。（2026-10-27 ユーザー決定、2026-10-28 に0.7から変更）
- 色：売り板は紫 `#8a3cff`、買い板は薄いグレー `#d9d9d9`。
- 棒の長さ：`min(枚数 ÷ ヒートマップの色の上限 U（7 節）, 1) × ヒートマップ本体の幅 × bookBarPct ÷ 100`。`bookBarPct` は設定（初期値10、つまり右端20%の空白の半分で最大）。基準は自前で計算せず、ヒートマップのものを使う。（2026-10-28 ユーザー決定。それまでは20%）
- 今の板の色の帯：最新の列より右（まだ来ていない時間の空白）を、最新の板（kind 3）で塗る。各価格の行を、ヒートマップと同じ色・同じ基準・同じ丸めと縮小の規則（1画素に複数の価格なら最大）で、最新の列の右端からヒートマップ本体の右端まで横一色に塗る。過去の板の色がそのまま今の板につながって見えるようにするため。400段の外は黒のまま。【確定】（2026-10-28 ユーザー決定）
  - 最新の列が画面の右端より右にある（過去を見ている）ときは、色の帯は画面に出ない。
  - 板の更新（250ミリ秒ごと）で塗り直すのは色の帯と棒の層だけ。ヒートマップの層は描き直さない。
  - リプレイでは再生位置の板で塗る。
- ライブで追いかけているときは、最新の列をヒートマップ本体の右端から20%手前に置く（右側の20%は、まだ来ていない時間の空白で、今の板の棒の場所になる）。過去へスクロールしたときは、その部分にもヒートマップが描かれ、棒が半透明で重なる。表示リセット（ダブルクリック／ダブルタップ）もこの位置に戻す。
- 縮小して1画素の高さに複数の価格が入るときは、合計せず最大の枚数を使う。
- 最良気配の帯は描かない（以前の案は、参照画像の買い板のグレーを帯と読み違えていた）。
- 過去へスクロールしても最新の板を出す。リプレイでは再生している位置の板を出す。
- ヒートマップや約定の層とは別の層で描き、板の更新でほかの層を描き直さない。描く順番は、ヒートマップ → 今の板の色の帯 → 現在の板の棒 → 価格ライン → 約定バブル → 現在値の点線。

### 7.3 大口板（Phase 6）【確定】（2026-10-27 ユーザー決定）

**判定は1秒の列で行う**

- 大口板の判定と、置かれている時間の追跡は、1秒の列（kind 1・2）で行う。ライブと過去で同じ処理になり、手元の列（2時間ぶん）から作り直せる。そのため、表示は最新の確定した列の時点になり、1〜3秒遅れる。
- 列ごとに、その列の両側の段（枚数1以上）の枚数のうち上位2%にあたる値（98パーセンタイル）を閾値とする。何％かは設定で変えられる（初期値2%）。設定画面は Phase 9 で、それまでは URL の `?bigTop=` で変えられればよい。不正な値なら2を使い、debug 表示に「bigTop 無効」と出す。

**置かれている時間の追跡（価格ごと）**

- その価格の枚数が閾値以上になった最初の列の秒を、置かれ始めた時刻とする。
- 枚数が「閾値 × 0.8」以上であるあいだは、置かれ続けているとみなす。閾値の揺れで出たり消えたりしないようにするため。
- 「閾値 × 0.8」未満になった列で、追跡を終える（次に閾値以上になったら、新しく数え直す）。
- その価格が400段の範囲の外に出たときは、追跡を終えずに保つ（7 節：400段の外は「注文がない」ではなく「分からない」）。範囲の外のまま5分たったら追跡を終える。範囲に戻ったら、その列の枚数で続けるか終えるかを決める。
- 3秒以上の列の欠け（7 節）をまたぐ場合は、追跡を終える。2秒以下の欠けは、直前の列の値で続ける。

**表示**

- 置かれている時間が5秒以上で、最新の列で置かれ続けている価格だけを、大口板列に横棒で出す。5秒は設定で変えられる（Phase 9）。それまでは URL の `?bigMinSec=` で変えられればよい。
- 範囲：受け取っている400段のうち、画面の価格帯に入るものすべて。
- 色：マゼンタ `#e040fb` の1色。買い板・売り板で色を分けない。
- 濃さ＝置かれている時間：5秒で不透明度0.35、300秒（5分）で1.0、その間は直線で変える。5分以上は1.0。
- 棒の長さ：表示中の大口板の中の最大の枚数を、列の幅いっぱいにする（それに対する割合）。大口板は上位2%なので、ヒートマップの基準（上位1%）を使うとほとんどが頭打ちになるため。
- 縮小して1画素の高さに複数の価格が入るときは、枚数が最大のものを使う（濃さもそのものの時間）。
- ヒートマップ・約定・現在の板の層とは別の層で描き、ほかの層を描き直さない。

### 7.4 VP（Phase 7）【確定】（2026-10-27 ユーザー決定）

**集計期間：当日のセッション**

- セッションは CME の1日：米国中部時間（America/Chicago）の17:00に始まり、取引は翌日16:00に終わる（日本時間では夏時間の間 7:00〜翌6:00、冬時間の間 8:00〜翌7:00）。週の始まりは日曜17:00。16:00〜17:00 は休止。
- 集計の区切りは17:00から翌日17:00の直前まで。休止中（16:00〜17:00）に万一約定があれば、終わる側のセッションに含める。【確定】（2026-10-28、Phase 7 で指定）
- 17:00 を過ぎたら新しいセッションとして集計をゼロから始める。
- スクロールや拡大縮小では変わらない。リプレイでは、再生している位置が属するセッションの始まりから再生位置までを集計する。

**集計はサーバーで行う**

- ブラウザの手元の約定は2時間ぶんしかないため、VP はサーバーで集計する。
- 価格（1ティック）ごとに、買い（アグレッサーが買い）と売りの枚数を合計して持つ。
- 起動時に、セッションの始まりから L（ライブの最初の確定列）までの約定を、保存済みのファイル（9 節）と履歴API（`/v1/history/ticks`）から取り込む。以後はライブの約定を足していく。取り込みの細部は 9 節。
- 取り込みが終わるまでは、取り込み済みの範囲だけで集計し、「取り込み中」であることを配信で知らせる（8.3 の `vp`）。
- 約定は内容で重複を消さない（6 節）。履歴とライブのつなぎ目は、列と同じ L で分ける（履歴は L より前、ライブは L 以降）。
- L が決まる前に受信した約定：時刻が L 以降のものは、L が決まったときに1回だけ足す。L より前のものはライブ側では足さない（履歴の取り込みで数える）。【確定】（2026-10-28。Phase 7 で、L が決まる前の36約定が VP から漏れていたのを直した）

**表示**

- VP の領域に、価格ごとの横棒を右から左へ伸ばして描く。長さは、そのセッションで出来高が最大の価格（POC）を領域の幅いっぱいにした割合。
- 棒の色：通常はグレー `#d9d9d9`、バリューエリアの中はオレンジ `#f5a623`、POC は白 `#ffffff`。
- POC の出来高が同じ価格が複数あるときは、高いほうの価格を POC にする。【確定】（2026-10-28、Phase 7 で指定）
- バリューエリア：POC から始め、上下の隣の価格のうち出来高の多いほうを1ティックずつ足していき、合計がセッションの出来高の70%以上になるまで広げた範囲。同じなら上を先に足す。
- POC の高さに白い点線（1px、2px線・2px隙間）を引く。VAH（バリューエリアのいちばん高い価格）と VAL（いちばん低い価格）の高さにも、オレンジ `#f5a623` の点線（1px、2px線・2px隙間、不透明度0.8）を引く。3本とも、VP の領域の右端から大口板列の左端まで伸ばす（ヒートマップと価格軸には引かない）。【確定】（2026-10-28 ユーザー決定。それまで POC の線は VP の幅だけ）
- VAH〜VAL の間の VP の領域の背景を、薄いオレンジ（`#f5a623`、不透明度0.12）で塗る。棒より下に描く。VP の領域の外には塗らない。【確定】（2026-10-28 ユーザー決定）
- 価格軸の列に、POC・VAH・VAL の価格のラベルを出す（UI_SPEC 3.10）。
- 縮小して1画素に複数の価格が入るときは、VAH・VAL・POC を含む行の位置に線を引き、帯もその行までにする。
- 縮小して1画素の高さに複数の価格が入るときは、出来高を合計して1本にする（VP は量の分布なので、最大ではなく合計）。その中に POC があれば白、バリューエリアの価格が1つでもあればオレンジ。
  - このときの棒の長さは、画面に出ている行の合計のうち最大のものを VP の幅いっぱいにする。【確定】（2026-10-28、Phase 7 で指定）
- ほかの層とは別に描き、ほかの層を描き直さない。更新は1秒に1回まで。

### 7.5 デルタヒストグラム（Phase 8）【確定】（2026-10-27 ユーザー決定）

- 1本の幅（集計の秒数）は、画面の拡大率に合わせて自動で選ぶ：1秒・5秒・15秒・60秒・300秒のうち、1本の幅が3 CSS px 以上になる最小のもの。
- 1本の値＝その区間の買いの枚数 − 売りの枚数（7.1 の約定の集計を使う）。区間の区切りは取引所時刻で、秒数の倍数に合わせる（例：15秒なら毎分 0・15・30・45 秒）。
- ＋は白 `#ffffff` で上向き、−は紫 `#a64dff` で下向き。0 の線を中央に引く。約定のない区間は描かない。
- 高さの基準：画面に見えている区間の |デルタ| の最大を、上下それぞれの高さいっぱいにする。
- 時間軸はヒートマップと共通。ライブでは、最新の区間を約定が来るたびに伸ばす。確定前の今の区間は、最新の列より1本ぶん右に出てよい（Phase 8 で約7.5px）。
- 価格軸の列の下段（デルタの目盛り）に、+最大値・0・−最大値の数値を出す。今の1本の秒数も小さく出す。
- ほかの層とは別に描き、ほかの層を描き直さない。

## 8. サーバーの動作

### 8.1 上流（TICK STREAM）への接続【確定】

- 接続は常に1本。新しく張る前に、古いソケットを必ず閉じる。プロセスが止まるとき（SIGTERM・SIGINT）もソケットを閉じてから終わる。
- 再接続：自分で閉じたとき以外は、close コードに関係なく再接続する。待ち時間は 1秒から倍々に増やし、上限60秒。ばらつき（±20%）を入れる。接続が5分続いたら待ち時間を1秒に戻す。
- コード 4029（接続数超過）のときは、最初の待ち時間を60秒にする。
- 死活監視：30秒間なにも届かなければ、接続が死んだとみなして閉じ、再接続する。
- 再接続したら購読（約定・板）をやり直す。
- 開発中にファイル変更で自動再起動する仕組みを使う場合も、古いプロセスの接続が残らないようにする。

### 8.2 状態ページ（Phase 1 のみ。後で画面に置き換える）

- `GET /status` で、テキストか JSON を返す。
- 中身：接続状態、接続した時刻、再接続の回数と直近の理由、最後に受信した時刻、`type` ごとの件数、5.5 の各件数、最新の板の最良気配と段数、直近の約定数件。
- APIキー、キーを含む URL は出さない。

### 8.3 ブラウザへの配信（Phase 2 以降）

**方式**【確定】（2026-10-27）

- WebSocket（`ws` パッケージ）。パスは `/ws`。Replit のプレビューの経路で `/api/` を付けないと届かない場合は `/api/ws` にしてよい（状態ページが `/api/status` になったのと同じ理由）。
- 列と板はバイナリ、それ以外は JSON で送る。列を JSON にすると30分ぶんで数十MBになり、iPhone の回線では重すぎるため。
- 列と板のバイナリは、9 節の列のレコード形式をそのまま使う。保存と同じ変換処理を使い回す。
- WebSocket の圧縮（permessage-deflate）を使う。板を250ミリ秒ごとに送るだけで、圧縮なしでは1時間に100MB前後になるため。保存した列は gzip で10分の1以下に縮んでいる。【確定】（2026-10-27）
- ブラウザからは TICK STREAM に直接つながない。同時に接続できるブラウザは5台まで。

**バイナリのフレーム**（リトルエンディアン）

| 項目 | 型 | 内容 |
| --- | --- | --- |
| kind | uint8 | 1 = 確定した列、2 = 範囲の列（履歴の応答）、3 = 現在の板 |
| reqId | uint32 | kind 2 のときは要求の番号、それ以外は 0 |
| count | uint32 | 続くレコードの数 |
| records | 9 節の列のレコード × count | kind 3 では、tsSec は板の取引所時刻の秒、source はその板の出どころ |

**JSON のメッセージ**（サーバー → ブラウザ）

| type | 内容 | タイミング |
| --- | --- | --- |
| `hello` | 銘柄、ティックサイズ（0.25）、列の幅（1秒）、サーバー時刻、モード（`live` か `replay`）、保存してある範囲 | 接続直後 |
| `trades` | 約定のまとめ（SPEC 6 の `Trade` の配列） | 250ミリ秒ごと（約定があるときだけ） |
| `rangeTrades` | 範囲の約定（要求への応答。`reqId` 付き） | 要求のあと、kind 2 の直後 |
| `rangeDone` | 範囲の応答の終わり。`{type:"rangeDone", reqId, fromSec, toSec, columns, trades, chunks}` | 要求への最後の応答 |
| `status` | 上流の接続状態、取り込みの進み具合、欠けの区間、5.5 の件数 | 変化したとき、ほかに10秒ごと |
| `error` | 要求の誤りなど（`reqId` 付き） | 要求のあと |
| `vp` | セッションの VP の全体。`{type:"vp", sessionStartSec, upToSec, loading, levels:[[価格ティック, 買い, 売り], …]}`（`loading` は取り込み中なら true） | 接続直後、セッションが替わったとき、取り込みが終わったとき |
| `vpUpdate` | 前回から変わった価格だけ。`{type:"vpUpdate", sessionStartSec, upToSec, levels:[[価格ティック, 買い, 売り], …]}`（値は差分ではなく、その価格の新しい合計） | 1秒ごと（変化があるときだけ） |

**JSON のメッセージ**（ブラウザ → サーバー）

| op | 内容 |
| --- | --- |
| `range` | `{op:"range", reqId, fromSec, toSec}`：その範囲の列と約定を要求する。1回の範囲は60分まで |

**流れ**

- 接続直後：`hello` → 直近30分の列（kind 2、reqId 0）と約定（`rangeTrades`、reqId 0）→ `rangeDone`（reqId 0）→ その後はライブ。
- 範囲の応答（接続直後の30分と `range` 要求の両方）は、5分（300秒）ずつに分けて送る。1つの区切りごとに kind 2 の列 → `rangeTrades` の順で送り、最後に `rangeDone` を送る。1フレームが大きくなりすぎて、送信待ちの上限に自分で引っかかるのを防ぐため（Phase 3 で、60分の応答が1フレーム約23MBになり、16MB の上限で接続が切れた）。【確定】（2026-10-27）
- 範囲の応答の区切りは、送信待ちが 4MB 未満になってから次を送る。
- ライブ：列は確定するたびに kind 1、板は250ミリ秒ごとに最新の1件だけ kind 3、約定は250ミリ秒ごとに `trades`。
- 過去へスクロールしたときは、ブラウザが `range` で要求する。
- 混雑時（範囲の応答を送っていないとき）：ブラウザの送信待ちが 4MB を超えたら、板（kind 3）を送らず次の最新を待つ。列と約定は落とさない。16MB を超えたら、そのブラウザの接続を閉じて記録する（ブラウザは再接続して取り直す）。

**リプレイ**【確定】

- `/ws?mode=replay&from=<Unix秒>&speed=<1|2|5|10>` で接続すると、保存した列と約定を、ライブと同じメッセージで流す。
- 列の確定（kind 1）は記録の時刻の間隔を速度で割って送る。板（kind 3）は、その秒の列をそのまま送る（保存しているのは1秒ごとの板だけなので）。約定は記録の時刻どおりに250ミリ秒ごとにまとめて送る。
- 保存した範囲の終わりまで来たら、`status` で終わりを知らせて止まる。
- リプレイ中も、ほかのブラウザのライブ配信と TICK STREAM の受信は止めない。

- 設定の読み書きは REST（`GET/PUT /api/settings`）。中身は 9 節の「設定」。【確定】（2026-10-28、Phase 9）

## 9. 保存

**方針**【確定】

- 板の生データは録画しない。ヒートマップ用に集計した列だけを保存する。（2026-10-25 ユーザー決定）
- 列はライブの板からも、過去の板（`/v1/history/book`）からも、同じ集計処理で作る。
- 集計方式を変えたくなったら、過去の分は履歴APIから取り直して作り直す。

**過去の板の取り方**【確定】（Phase 0 で10分間・9境界を検証済み）

- 60秒ごとの窓に区切り、`limit=500000` で1窓ずつ順に取得する。並列にしない。
- `truncated=false` を確かめる。`true` なら窓を半分に分けて取り直す（1秒未満には分けない）。
- 応答には `end` の秒の端数まで含まれるため、`start×1,000,000 ≤ ts < (start+60)×1,000,000` の行だけを使う。これで窓どうしの重複も欠けも出ない。
- 1分ぶんで約2.5〜5秒かかる（1時間で約3〜5分）。バックグラウンドで順に取り、作った列を保存する。2回目からは保存した列を使う。
- 429 などのレート制限が返ったら、`Retry-After` があればそれに従い、なければ60秒待ってから再開する。
- 通信の失敗・5xx・タイムアウトは、60秒待って取り直す。同じ窓で3回失敗したら、その窓は取り込まずに欠けとして記録し、状態ページに出して次の窓へ進む。【確定】
- 終わりが現在から5分以内の窓は、すぐには取らず、現在が「窓の終わり＋5分」を過ぎてから取る。履歴APIへの反映が数分遅れ、早く取ると末尾が欠けるため（Phase 2a で0行と末尾だけの欠けの両方が起きた）。待っている間も、ほかの窓とライブは進める。【確定】
- それでも、終わりが現在から10分以内の窓で0行が返ったら、2分待って取り直す。3回取り直しても0行なら「データなし」として記録する。【確定】
- 約定の履歴（`/v1/history/ticks`）も、同じ60秒窓・半開区間の方式で取る。

**起動時の取り込み（バックフィル）**【確定】（2026-10-26 ユーザー決定）

- ライブで最初に確定した列の秒を L とする。起動時に、[L − 3時間, L) の板と約定を履歴から取り込む。
- L より前は履歴、L 以降はライブ。つなぎ目の秒 L の約定は、接続前の分が欠けることがある。欠けを埋めず、つなぎ目の秒として記録する。
- 新しい窓から順に（L の直前から過去へ）取り込む。最近の分から先に使えるようにするため。
- すでに保存してある秒は取り直さない。
- 休場中（毎日の休止、週末）は履歴が0行になる。0行の窓はそのまま「データなし」として扱う。
- 切断などでライブに欠けた区間は記録し、状態ページに出す。欠けを履歴で埋めるのは後のフェーズで決める。

**VP のための約定の取り込み**【確定】（2026-10-27）

- 起動時に、当日のセッションの始まり（7.4）から L までの約定をそろえる。
- 保存済みの約定のファイルがある時間は、ファイルから読む。ない時間は `/v1/history/ticks` から取り、保存もする（9 節の約定の保存形式）。
- 約定の履歴は軽いので、VP のための取り込みでは15分ごとの窓で取ってよい（`limit=500000`、半開区間、`truncated=true` なら半分に分ける、1窓ずつ順に、今に近い窓は5分待ってから）。
- 「保存済み」は、ファイルがあるかではなく、取得済み区間の記録（`coverage.json`）で判断する。ファイルがあっても記録でそろっていない区間は、足りない区間だけを取る。15分より長い区間は15分以下の窓に分ける。保存済みの区間と重ねて取らない。【確定】（2026-10-28、Phase 7 で指定）
- 取った約定は、既存の約定のファイル（同じ形式）に組み込む。別の補完ファイルは作らない。既存の行は内容も順番も変えず、足りない区間の行だけを時刻の位置に入れる。一時ファイルに書いてから置き換え、置き換えが済んでから `coverage.json` を更新する。【確定】（2026-10-28）
- 同じ窓で3回失敗したら、その窓は欠けとして状態ページとログに出し、その窓を除いた集計で `loading: false` にする。【確定】（2026-10-28）
- 板の3時間の取り込みと並べて走らせず、板の取り込みのあとに行う。ライブの受信は止めない。
- 進み具合は状態ページに出す。

**保存形式**【確定】

- 列のファイル：1時間（UTC）ごとに1ファイル。`columns/NQ/1s/{YYYY-MM-DD}/{HH}.bin`。その時間が終わったら gzip して `{HH}.bin.gz` にし、元の `.bin` は消す。
- 列のレコード（リトルエンディアン、秒の昇順に追記）：

| 項目 | 型 | 内容 |
| --- | --- | --- |
| tsSec | uint32 | 列の秒（Unix 秒） |
| source | uint8 | 0 = ライブ、1 = 履歴 |
| nBids | uint16 | 買いの段数 |
| nAsks | uint16 | 売りの段数 |
| bids | (int32 価格ティック, uint32 枚数) × nBids | 最良から順 |
| asks | (int32 価格ティック, uint32 枚数) × nAsks | 最良から順 |

- 1列は最大約6.4KB、1時間で最大約23MB（gzip 前）。
- 約定のファイル：1時間（UTC）ごとに `trades/NQ/{YYYY-MM-DD}/{HH}.jsonl.gz`。1行1約定で、SPEC 6 節の `Trade` をそのまま JSON にする。
- 保存先は「列と約定の保存」というインターフェースにまとめ、開発中はローカルの `data/` に書く実装だけを作る。App Storage の実装は公開（Phase 10）のときに足す。
- 開発中のローカル保存は7日より古いファイルを消す。【確定】（2026-10-26 ユーザー決定）
- 開発中（Workspace）はローカルの `data/` に書いてよい。`data/` は Git と公開物の対象外（`.gitignore`、`.replitignore`）。【確定】

**設定**【確定】（2026-10-28 ユーザー決定、Phase 9）

- サーバーに1組だけ持ち、どの端末からも同じ設定を使う。
- 保存先は「設定の保存」というインターフェースにまとめ、開発中は `data/settings.json` に書く実装だけを作る。App Storage の実装は Phase 10 で足す。7日削除の対象にしない。
- 書き込みは一時ファイルに書いてから置き換える。
- 項目（設定画面に出すのはこの20個だけ）：

| キー | 内容 | 初期値 | 受け付ける値 |
| --- | --- | --- | --- |

- URL の `?bubbleMin=`・`?bigTop=`・`?bigMinSec=` は確認用に残す。保存した設定より優先し、そのタブでだけ効く。保存はしない。

**公開時の保存（App Storage）**【確定】（2026-10-28、Phase 10a）

- 公開先（Reserved VM）では、列・約定・取得済み区間の記録（`coverage.json`）・設定を App Storage に置く。デプロイ環境のファイルシステムは再デプロイで消えるため。Node からは `@replit/object-storage` を使う（依存の追加はユーザーが承認済み）。
- 保存の実装は「列と約定の保存」「設定の保存」のインターフェースの裏に足す。どちらを使うかは起動時に環境で決める：公開先は App Storage、開発（Workspace）は今までどおりローカルの `data/`。開発で App Storage の実装を試すときだけ、環境変数で App Storage に切り替えられるようにする。
- 開発と公開先が同じバケットを使う場合に備え、オブジェクトの名前の先頭を `prod/`（公開先）と `dev/`（開発で試すとき）に分ける。公開先かどうかは Replit が公開先に設定する環境変数で判断する（どの変数かは実装時に確かめて報告する）。2つのサーバーが同じ名前に書くことがないようにする。
- 名前：`{prod|dev}/columns/NQ/1s/{YYYY-MM-DD}/{HH}.bin.gz`、`{prod|dev}/trades/NQ/{YYYY-MM-DD}/{HH}.jsonl.gz`、`{prod|dev}/coverage.json`、`{prod|dev}/settings.json`。中身の形式はローカルと同じ。
- App Storage は追記ができないので、書き込み中の1時間はローカルのディスクに今までどおり書く。その時間が終わったら gzip してアップロードし、成功を確かめてから `coverage.json` を更新する。アップロードに失敗したら、ローカルのファイルを残したまま、待ち時間を延ばしながら取り直し、状態ページに出す。
- `coverage.json` には、App Storage に上がった範囲だけを記録する。再起動や再デプロイでローカルの書きかけが消えても、その範囲は「保存されていない」扱いになり、起動時の取り込み（9 節）が履歴から取り直す。
- 範囲の応答とリプレイで使うファイルは、ローカルのディスクにキャッシュする。最近48時間分を目安に、古いものから消す。キャッシュにない時間は App Storage から取ってくる。
- 公開先では、列と約定を消さない（7日の削除をしない）。（2026-10-28 ユーザー決定）開発のローカルは7日で消すまま。

## 3. 全体構成【確定】

```
TICK STREAM ──(WebSocket 1本: 約定・板)──▶ サーバー（Node.js + TS, 1プロセス）
            ──(REST: 過去の約定・板)────▶   ├ ingest      受信・正規化
                                           ├ book        板の状態管理（全量置き換え）
                                           ├ aggregate   ヒートマップ列・集計・間引き
                                           ├ history     REST から過去の板・約定を取得し、列を作る
                                           ├ store       集計した列と約定の保存（App Storage）
                                           └ hub         ブラウザへの配信（WebSocket）
                                                 │
                                                 ▼
                                   ブラウザ（Safari / iPad / iPhone）
```

- TICK STREAM への WebSocket 接続はサーバーから1本だけ。ブラウザが何台つながっても増やさない。
- ブラウザは TICK STREAM に直接つながない。APIキーはサーバーだけが持つ。
- ライブの板と過去の板は、同じ集計処理（aggregate）を通してヒートマップの列にする。

- 公式 Node SDK を使わない理由（Phase 0 で公開ソースを確認）：購読フレームが公式資料と違う（`action` と `op`）、接続先に `/stream` が付かない、JSON の ping に応答しない、キーの先頭12文字をログに出す経路がある、桁数から時刻の単位を推測する。【確定】

- デプロイ環境のファイルシステムは再デプロイで消える。永続化するものは App Storage に置く。【確定】

## 5. TICK STREAM のデータ

### 5.1 分かっていること【確定】

**接続**

- WebSocket：`wss://stream.tick-stream.xyz/v1/stream?key=…&symbols=NQ`。約定は URL の `symbols` で、板は同じ接続で `{"op":"subscribe","channel":"book","symbols":["NQ"]}` を送って購読する（実測で動作確認）。
- 全フレームに `type` がある（約定も含む）。`welcome`、`feed`、`warning`、`error`、`ping`/`pong` がある。
- サーバーは15秒ごとに ping を送る。`{"op":"pong"}` で応答する（実測で動作確認）。45秒応答がないと切断される。
- 接続数の上限：L2 プランで3本。切れたソケットは最大45秒枠を占有する。超えるとコード 4029。
- 銘柄はルート指定（NQ）で、期近への乗り換えは自動。

**ライブの板（`book`）**

- 毎回、全量のスナップショットが届く。差分ではない。（公式資料）
- 項目：`type`, `symbol`, `bids`, `asks`, `imbalance`, `ts`。`bids` / `asks` は `[price, size]` の配列で、最良価格から順に並ぶ。片側最大400段。（公式資料・実測）
- 銘柄ごとに間引かれて届き、最大でおよそ7回/秒。（公式資料）
- `ts` は Unix 秒。秒精度しかない。（実測）

**ライブの約定（`ticks`）**

- 項目：`type`, `symbol`, `price`, `size`, `side`（アグレッサー側 `buy`/`sell`）, `exch`, `ts`。
- `ts` は公式資料では Unix 秒。実測はまだ。【要検証】

**REST**

- ベース URL：`https://api.tick-stream.xyz/v1`、`Authorization: Bearer <key>`。
- 範囲指定の `start` / `end` は Unix 秒。応答には `end` の秒の端数（`end` 秒＋0.9秒前後）まで含まれる。（実測）
- `GET /v1/ticks`（symbol, start, end）：直近の約定。start なしだと1時間分のみ。7日前まで遡れる。行の `ts` はマイクロ秒。（実測）
- `GET /v1/history/ticks`（symbol, start, end, limit）：NQ の過去約定。行の `ts` はマイクロ秒。（実測）
- `GET /v1/history/book`（symbol, start, end, limit）：NQ の過去の板。（実測）
  - 1行が1つの価格段。項目は `ts`（マイクロ秒）, `side`（bid/ask）, `level`（1〜400）, `price`, `size`, `flag`。
  - 2026年6月中旬以降は、およそ250ミリ秒ごとのスナップショット。それより前は `flag` 付きの差分形式で、形式が違う。（公式資料）
  - 通常は同じ `ts` に800行（400段×両側）。寄り付きでは同じ `ts` に1,600行の箇所がある。理由は未確認。【要検証】
- `limit` の公式上限は500,000行。`limit=500000` で1分間の板（約19.5万行）が `truncated=false` で返った。取得に約5秒。（実測）
- 秒単位の `start` で次のページを取ると、1秒に1,000行を超える板では同じページに戻って先に進まない。秒単位のページ送りは使えない。（実測）

**データ量（実測）**

| 種類（1分間） | JSONL | gzip |
| --- | --- | --- |
| 板の履歴（寄り付き） | 約16.0MB | 約1.16MB |
| 板の履歴（通常） | 約16.1MB | 約1.17MB |
| 約定の履歴（寄り付き） | 約0.47MB | 約41KB |
| 約定の履歴（通常） | 約59KB | 約6KB |

## 6. 内部データ表現【確定】

境界（受信処理）で必ずこの形に変換し、以降は外部形式を使わない。

```ts
type TimeUs = number;      // Unix エポックからのマイクロ秒（整数）
type PriceTicks = number;  // 価格 ÷ ティックサイズの整数（NQ は 0.25）

interface Trade {
  tsUs: TimeUs;        // 取引所時刻（ライブは秒精度の可能性あり）
  recvUs: TimeUs;      // サーバー受信時刻。履歴から作ったものは tsUs と同じ値にする
  price: PriceTicks;
  size: number;
  side: 'buy' | 'sell'; // アグレッサー側
}

interface BookLevel { price: PriceTicks; size: number; }

// 板は毎回全量。受け取るたびに丸ごと置き換え、差分の適用はしない
interface BookSnapshot {
  tsUs: TimeUs;         // 取引所時刻（ライブは秒精度、履歴はマイクロ秒精度）
  recvUs: TimeUs;       // サーバー受信時刻。履歴から作ったものは tsUs と同じ値にする
  source: 'live' | 'history';
  bids: BookLevel[];    // 最良価格から順
  asks: BookLevel[];
}
```

- 時刻の単位変換は受信処理の1か所だけで行う。ライブの板の `ts` は秒なので ×1,000,000、履歴の `ts` はそのまま使う。
- 価格の整数化も受信処理の1か所だけで行う。
- 履歴の板は、同じ `ts` の行を集めて1つの `BookSnapshot` に組み立てる。1,600行の扱いは 5.2 の結果で決める。
- 2026年6月中旬より前の差分形式の履歴は扱わない。【案】

## 7. ヒートマップの集計

- ヒートマップは「時間の区切り（列）× 価格」のマスに、板の枚数を持つ。【確定】
- ライブの板は `ts` が秒精度で、同じ秒に複数届くため、どの列に入れるかはサーバー受信時刻（`recvUs`）で決める。履歴の板は `tsUs` で決める。【案】
- 列の幅（何秒で1列か）：【未決定】。初期値の案は1秒。
- 1列の値の決め方：【未決定】。候補は次の3つ。
  - 区間の終わりの時点の枚数
  - 区間内の最大枚数
  - 区間内の時間加重平均
- 注意：ライブは最大でおよそ7回/秒、履歴はおよそ4回/秒と、1列に入る板の回数が違う。「区間内の最大」はライブの方が大きく出やすいため、ライブと過去の見た目をそろえるなら「区間の終わり」か「時間加重平均」が向く。
- 価格の丸め：ティック幅で丸める（参考記事の方式）。丸め幅は設定で変えられるようにする。【案】
- 色のスケール：【未決定】。候補は「上限で頭打ち」「対数」「上位◯%カット」。現在の板の棒の長さと同じ方式にそろえる。

## 8. サーバー → ブラウザの配信

- 方式：WebSocket（パス `/ws`）。最初は JSON、重ければバイナリに切り替える。【案】
- 間引き：板と約定は 100〜250ミリ秒ごとにまとめて送る。【案】

| メッセージ | 内容 | タイミング |
| --- | --- | --- |
| `hello` | 銘柄、ティックサイズ、列の幅、サーバー時刻 | 接続直後 |
| `history` | 直近 N 分のヒートマップ列と約定 | 接続直後 |
| `column` | 確定したヒートマップ列 | 列の区切りごと |
| `book` | 現在の板（間引き後） | 100〜250ミリ秒ごと |
| `trades` | 約定のまとめ | 100〜250ミリ秒ごと |
| `status` | 上流の接続状態、警告の件数 | 状態が変わったとき |

- 設定の読み書きは REST（`GET/PUT /api/settings`）。【案】

## 9. 保存

**方針**

- 板の生データは録画しない。ヒートマップ用に集計した列だけを保存する。【確定】（2026-10-25 ユーザー決定）
- 列はライブの板からも、過去の板（`/v1/history/book`）からも、同じ集計処理で作る。【確定】
- 集計方式を変えたくなったら、過去の分は履歴APIから取り直して作り直す。【確定】

**過去の板の取り方**【案】

- 60秒ごとの窓に区切り、`limit=500000` で取得する。`truncated=false` を確かめ、`true` なら窓を半分に分けて取り直す。
- 応答には `end` の秒の端数まで含まれるため、`start×1,000,000 ≤ ts < (start+60)×1,000,000` の行だけを使う。これで窓どうしの重複も欠けも出ない。
- 秒単位のページ送りは使わない。
- 1分ぶんの取得に約5秒かかるため、バックグラウンドで順に取り、作った列を保存する。2回目からは保存した列を使う。
- 429 などのレート制限が返ったら、待ってから再開する。

**保存形式**【案】

- 列：価格ごとの枚数の配列をバイナリで持ち、1時間ごとのファイルにして App Storage に置く。
- 置き場所の例：`columns/{symbol}/{列の幅}/{YYYY-MM-DD}/{HH}.bin`
- 約定：軽い（寄り付きでも1分で gzip 約41KB）ので、生のまま gzip した JSON Lines で保存する。
- 開発中（Workspace）はローカルの `data/` に書いてよい。`data/` は Git の管理対象外にする。【確定】

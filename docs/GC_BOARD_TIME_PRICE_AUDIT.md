# GC保存板とMBO／MBP-10の時刻・価格・更新頻度調査

2026-11-06 JST。読み取りと研究用集計のみ。製品コード・製品データ・仕様・公開設定・稼働中の受信は変更していない。Publish・再起動・上流接続・購入なし。

## 結論

**数時間の時差、DSTの1時間ずれ、GC価格の倍率違い、買売の入れ違いでは説明できない。**
同じ秒・価格の約定数量は強く対応するのに対し、保存板のスプレッドは広く、最良気配の変化も少ない。
確認した正規化・列化・保存処理に、これを生む一定の価格変換は見つからなかった。

受信元のsnapshot/coalesce・時刻精度・取得経路の違いを有力候補として残す。ただし、**受信元の不正確な板と確定したわけではない**。
保存前の元フレーム、そのsubsecond時刻、限月識別子が残っていないため、配信元とアプリ内の入力選択の寄与は分離し切れない。原因未確定のまま補正・製品修正は行わない。

既存のMBP-10検証は11/03の05・14・23時台、計10,800秒・上位10段の価格と数量の完全一致。
この範囲ではMBO再構築を比較基準にできる。他の日や400段すべてまでMBP-10で独立確認した、という意味には拡張しない。

## 3. −2時間〜＋2時間の時刻探索

定義は`app(t)`対`MBO(t+δ)`。負のδはアプリのラベルを過去へ動かして比較する向き。
価格トレンドだけで高相関になるため、仲値水準だけでなく連続秒の差分相関・MAE・BBOも見る。

探索は±7,200秒を60秒刻み、観測順30件ごとに粗探索。上位3候補の±60秒を1秒刻み・5件ごとで精査。
その最良候補の±5秒と0・±3,600・±7,200秒を全観測で計算した。
日ごとの探索も同じ規則。変動のない系列の相関はnullとし、欠けを前値で埋めない。

| δ秒 | 比較秒 | 仲値相関 | 仲値MAE ticks | 1秒差分相関 |
|---:|---:|---:|---:|---:|
| −7,200 | 124,536 | 0.915195533 | 123.7901 | 0.00373 |
| −3,600 | 124,192 | 0.959201130 | 84.3094 | 0.00668 |
| −2 | 126,767 | 0.999986637 | 1.3264 | 0.10521 |
| **−1** | 126,767 | **0.999992468** | **1.0456** | 0.35668 |
| **0** | 126,767 | 0.999991722 | 1.1105 | **0.53146** |
| ＋1 | 126,766 | 0.999981258 | 1.6382 | −0.00235 |
| ＋3,600 | 123,226 | 0.965683728 | 78.9173 | 0.00547 |
| ＋7,200 | 122,625 | 0.914489294 | 118.6966 | 0.00073 |

大きなシフトではデータ端・休止・欠けで分母が変わるため、近傍は固定母数でも確認した。
全±6秒にMBOが存在し、その各秒にアプリ観測もある同一72,688秒に限定：

| δ秒 | 双方BBO一致秒 | 双方一致% | 仲値相関 |
|---:|---:|---:|---:|
| −2 | 3,515 | 4.836 | 0.999981383 |
| −1 | 5,266 | 7.245 | 0.999989993 |
| 0 | 6,156 | **8.469** | 0.999989208 |
| ＋1 | 2,839 | 3.906 | 0.999974092 |

**仲値水準が最も合う−1秒と、BBOが最も合う0秒は別。−1秒補正を製品へ適用する根拠にはならない。**
この近傍だけの相関差は微小で、秒への切捨てとフレーム位相・coalesce・時変遅延の候補は残る。
整数秒保存からsubsecond遅延を確定することはできない。

## 4. 価格の変換

- `appMid = a × referenceMid + b`の記述的OLS：
  **a=1.0000374152、b=−1.4873072 ticks**。価格帯約40,000 ticks付近では切片と傾きがほぼ相殺される。
  0.1/0.25の取り違え、10倍・1/10倍などの単位変換の形ではない。これを校正式として採用しない。
- 買BBO差（app−MBO）：平均−1.3433、中央値−1、p01/p95/p99は−8/＋1/＋2 ticks。
- 売BBO差：平均＋1.3247、中央値＋1、p01/p95/p99は−2/＋5/＋8 ticks。
  買売に同じ一定価格オフセットがある形ではない。
- 両側に共通の一定tick補正をかけた場合、最大の双方一致は**補正なし12,659秒**。
  同じずれ＋1は1,171秒、−1は1,162秒だけ。一定平行移動で一致にできない。
- 買売入替後の双方一致は**0秒**。正規対応の両側合計MAEは1.5426 ticks/側、
  入替は4.1520 ticks/側で、改善しない。
- spread：平均アプリ5.4668 / MBO2.7988 ticks、中央値5 / 3、p95は10 / 4。
- 共通126,767秒中、アプリspreadが広い108,632秒（85.69%）。
  アプリ買が低い／売が高いのいずれか112,654秒（88.87%）。
  同じ時刻の同じreal bookへimpliedを追加するだけでは、こうした気配の悪化は説明できない。
  入力時刻の違いが残るため、impliedの寄与自体を否定するものではない。

## 6. 保存約定との比較

同じ日付の既存アプリ約定74時間を、既存MBOのTだけと比較。Fを二重に約定へ足さず、正当な同時刻同価格別約定も重複削除しない。
単位は整数秒×整数ticks。同一セルの件数・合計枚数を別に照合する。

| UTC日 | app件数 | MBO件数 | app枚数 | MBO枚数 | 同秒・同価格で重なる枚数 |
|---|---:|---:|---:|---:|---:|
| 10/29 | 30,084 | 25,400 | 33,361 | 36,272 | 33,353 |
| 10/30 | 43,137 | 111,313 | 47,956 | 159,993 | 47,943 |

| 合計 | **238,713** | **340,734** | **263,606** | **486,823** | **263,518** |

このMBO合計はアプリ約定ファイルが存在する74時間全体。ファイルがあってもアプリの受信が時間全体で揃っているとは限らない。
比較の価格セルで`min(app枚数, MBO枚数)`を取った総和が最終列であり、同一イベントのID照合ではない。

- **アプリ数量の99.9666%**が同秒・同価格のMBO数量に収まる。超過は88枚。
  保存されている約定の時刻・価格に大規模な別時刻・別価格への変換は認められない。
- ただしMBO486,823枚に対してアプリ263,606枚なので、**全約定が完全一致したわけではない**。
  未受信・保存の欠け・配信対象やunknown side・約定の分割単位は区別が必要。
- アプリに約定が実在する秒だけに絞ったMBO合計266,026枚に対してもアプリは263,606枚（99.0903%）。
  アプリに約定のない秒を無条件に「取引なし」と判断しない。
- 秒価格セルの枚数一致は127,540セル。一方、件数と枚数の両方一致は95,312セル。
  枚数は同じでアプリ件数が多いセルが32,228。例：
  `tsSec=1793289599, priceTicks=40351`でapp2件2枚、MBO1件2枚。
  1注文の分割単位・レコード粒度の違いがあるため、件数差を全て欠損や二重計上と解釈しない。
- 同一秒の出来高加重価格差MAEは**0.00790 ticks**。秒単位VWAPが両方ある秒に限定した値。
- 同秒・価格の重なる枚数はδ0で263,518、−1で28,214、＋1で28,173、−5で15,001、＋5で15,004。
  ±5秒は隣の時間ファイルも探索。UTC日を跨ぐ端は探索外なので、大きなシフトの欠損率をこれで評価しない。
- appの明示contractはGCZ6 125,105件、不明113,608件。他限月の保存記録は0。
  unknown sideはapp0枚、MBO5,882枚。これらを同じ方向分布とはみなさない。

**「約定も板と同様に数時間ずれている」結果ではない。保存された約定の時刻・価格は強く合うが、板の状態は合わず、約定の総量も完全ではない。**

## 7. 受信→保存のコード確認

現行ソースを確認した。各保存時間の公開commit・当時の受信生フレームは今回特定していない。
これを、保存当時の公開処理を完全に再現した検証とは言い換えない。

| 場所・関数 | 変える内容／変えない内容・注意 |

| `server/src/ingest/normalize.ts:normalizeTime` | liveの整数Unix秒×1e6、historyのusはそのまま。UTC/CT/DST変換なし |

| `server/src/ingest/receiver.ts:Receiver.snapshot` | normalizeの結果をbookへ全置換しobserverへ渡す。差分板の合成ではない |

| `server/src/aggregate/columns.ts:accept/finish/expire` | 秒ラベルfloor(tsUs/1e6)、受理最大tsのsnapshotを採用。同tsなら後着を採用。新秒/expireで確定。確定後の秒は拒否。平均・合成・欠損埋めなし |
| `server/src/history/decode.ts:historyColumns` | 同tsの完全800行組の最後を選び、sideごとlevel昇順へ並べて同じnormalizeへ。historyも秒内の最後の板 |
| `server/src/pipeline.ts:Pipeline.constructor/book` | 確定したcolumnを`store.addColumns`と配信へ。価格計算なし |
| `server/src/store/local.ts:addColumns/writeHour` | 秒順、既存秒優先でマージ。既存history/liveの秒を後の別snapshotで差し替えない。鮮度の制約は残る |
| `server/src/store/records.ts:mergeColumnRecords` | 保存済みrecord byteを維持し、不在秒だけ挿入。段内の順序は変えない |
| `server/src/store/binary.ts:encodeColumns/decodeColumns` | UInt32秒、source、side長、Int32価格tick、UInt32数量。bids→asksの順を対称に保存・復元 |

### 隔離確認

75時間の保存ファイルから**356列**を採取し、実際の`normalizeBook → ColumnAggregator → encode/decode`へ通した。
全列の時刻・source・両側全段の価格・数量がdeepEqual、拒否0。writerやサーバーは起動していない。
保存済みsnapshotを再入力した試験であり、失われた受信元フレームまで検査したわけではない。

比較対象のsource別双方一致：
- history：2,023 / 20,168 = 約10.03%。
- live：10,636 / 106,599 = 約9.98%。

historyだけの不具合として切り分ける結果でもない。
ライブは整数秒なので、その秒の最大元イベント時刻を保持できず、到着順と真のイベント順の違いは残る。
既存秒優先・確定秒への後着拒否は入力選択に影響し得るが、今回の保存データだけでは寄与を定量確定できない。

## 8. 原因の確度と、修正する場合の案（未実施）

| 候補 | 判定と根拠 |
|---|---|
| UTC/CT・DSTで1時間ずれ | 今回の大きな不一致の説明として支持なし。全日で最良lag−1秒付近、±1時間でMAEが大幅増 |
| 一定tick・倍率・side取り違え | 支持なし。価格差は買売逆符号で可変、価格回帰はほぼ1倍、swap0一致 |
| MBO再構築上位10段の不良 | 既存の3時間MBP-10独立一致では検出なし。他全日時の保証ではない |
| アプリの価格変換・バイナリ化の不具合 | 現行コードと356列往復で検出なし。当時の生フレームは未確認 |
| coalesce・秒精度・取得位相 | 有力候補。公式仕様と、低い変化頻度・0/−1秒近傍の差・約定側の強い対応に整合。ただし単独原因と未確定 |
| 受信元の板数量／構成の違い | 有力候補だが未確定。spread・深度の差があり、限月・impliedの仕様確認が必要 |
| 遅着拒否・既存秒優先 | コード上の影響経路は存在。元フレーム不在で今回の寄与量は不明 |
| 異限月 | 板識別子がなく未確定。既知約定はGCZ6のみで、積極的な別限月の根拠なし |

根拠なしに時刻・価格・数量を補正しない。アプリ側を修正するなら、先に次の対照が必要：

1. 同一の受信bookに識別子を付け、元のts・recvUs・contract・正規化前後・確定秒・拒否理由を少量採取して照合。
   関係候補は`Receiver.snapshot`、`normalizeBook`、`ColumnAggregator.accept/finish`、`LocalStore.writeHour`。
2. 受信元payload自体がCMEと違えば、保存ロジックの補正では直さない。配信元に同時刻・同限月の差分例を照会する。
3. 元フレームは正しいのに列が違えば、同じ記録入力を隔離再生し、同秒後着・秒境界・既存秒優先の最小修正を決める。
   空秒を作らない・正当な数量と順序を変えない試験を追加する。

今回は診断追加も製品へ実装していない。採取負荷・機密ログ・保存容量・遅着の二重採用がリスクで、変更時は別途承認が必要。

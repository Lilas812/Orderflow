# 本番の保守手順：購入42日と修正版を一度の停止で反映する

## 今回の作業範囲

開発側で次の4点を修正した。本番の停止・日次本体への反映・Publishは今回行わない。

1. LONG VPから起動時backfill／VP履歴の完了待ちを除いた。
   CT16:55（ET17:55）には別のタイマーで保存済み原約定を読む。履歴APIや共通履歴ロックを待たない。
   未保存区間・未確定の終端をgapsに残して不完全日を保存し、既存の直近7日再構築で補完する。
   CT17時までの保存境界とCT17:05以降の成熟済み最終集計は維持する。
2. 日次アップロード直前にクラウドの世代と本文を読み直し、最新版を基準にimprovesDayを判定する。
   更新はifGenerationMatch付き。409／412等で競合したら本文から読み直して再判定し、4回で収束しなければ明示的に失敗する。
   旧キャッシュから無条件でアップロードしない。prodで世代対応アダプターがなければ書込みを拒否する。
3. network_or_timeoutは広い窓を同じまま3回要求せず、分割可能なら最初の失敗で半分程度に分割する。
   通常の15分窓は分単位で二分し、最小1分にする。coverage境界由来の端数窓は1分未満へ新たに分割せず、分割できない端数も最大3回でgapにする。
   1分窓は初回を含む計3回でgapにし、成功した他の子窓は保存して次へ進む。
   429・5xx・切詰め・0行の既存扱いは維持する。失敗ログにはsymbol・kind・start・end・elapsedMs・失敗理由を出す。
4. long_vp_failedに元の例外名・message・stack・code・cause連鎖を追加した。
   GC/NQを明示し、既存の認証値除去を通して出力する。

CT16:55の保存はネットワークが正常でもI/O時間が必要。タイマーがその時刻に起動する設計であり、
App Storage障害やディスク障害中まで「必ず時刻内に保存成功する」とは保証しない。
統合後の記録済み保存はlong_vp_failed（reason: daily_checkpoint_failed、mode: recorded_only）で失敗を記録し、分ごとの監視で再試行する。より良い日次が既にある場合は保全する。

仕様正本は書き換えていない。ユーザーの今回のCT16:55の不完全保存指定と、既存の終端後の確定指定を分けて実装した。

## 停止時間の見込み

**通常の作業枠として15〜25分を確保する。実測済みの所要時間ではなく、安全側の初期見積り。**

| 停止中の作業 | 目安 |
|---|---:|
| 公開停止の確認・直前日次の採取・原本バックアップ | 2〜4分 |
| 42日次の条件付き反映・再ダウンロード・全日照合 | 3〜6分 |
| 修正版の公開処理・起動・保存データ復元 | 4〜8分 |
| 起動後の最小確認・予備 | 3〜7分 |

前回は元の日次が4ファイルだったが、実施時までに増える可能性がある。
通信再試行、App Storage応答、ビルド待ち、起動復元で延び得る。制限時刻を超えても検証を省略しない。
必要なら停止中のまま復帰を判断する。履歴の全補完は公開再開後に進むため、その完了まで受信を停止し続ける必要はない。

## B. ユーザーが公開を止める

1. ユーザーが**公開側**の停止操作を行う。WorkspaceのRun停止ではない。
2. 公開コントロール側で停止が確認され、旧プロセスが書けなくなったことを確認する。
   非認証アクセスのReplShield転送、画面が見えないこと、保存ログがしばらくないことだけでは停止確認としない。
3. 停止確認の記録を`data/longvp-maintenance/stopped-proof.json`に保存する。
   保守CLIは次の形式の20分以内の記録を要求する。

```json
{"success": true, "isDeployed": false, "checkedAt": "停止確認を実際に取得したUTCのISO時刻"}
```

この記録は運用者による監査用確認で、偽造不能な証明やサービスを止める機能ではない。
公開状態取得が停止と判断できなければ反映しない。作業が20分を超える場合は本当に停止継続中かを確認し直して更新する。
公開アプリは42日反映・照合完了まで再開しない。

## C. 停止直後の原本を保存する

新しい出力先を使う。既存出力先を上書きしない。次のEXAMPLEは実施ごとに一意な名前へ置き換える。

```sh
node server/tools/capture-longvp-maintenance.ts \
  --days-only --out=data/longvp-maintenance/EXAMPLE-pre

node server/tools/backup-approved-longvp.ts \
  --inventory=data/longvp-maintenance/EXAMPLE-pre/inventory.json \
  --out=data/longvp-maintenance/EXAMPLE-backup
```

- --days-onlyでは調査用の原約定50時間を再取得せず、LONG VP原本だけを採取する。
- クラウドの新しい`prod/backup/longvp/<実行時刻>-<識別子>/`に既存対象の元バイト列を保存し、
  件数・SHA-256・元世代・バックアップ世代・元々存在しない対象をmanifest.jsonへ記録する。
- 再ダウンロードしてハッシュ一致を確認する。世代が変わったら中断する。
- バックアップ数は実施時の元ファイル数。以前と同じ4件だと決めつけない。
- ローカルの`EXAMPLE-backup/backup-manifest.json`と`backup-result.json`も保全する。

## D. 購入42日を反映して全日照合する

```sh
node server/tools/run-approved-longvp.ts \
  --action=apply \
  --plan=data/longvp-maintenance/approved-days/plan.json \
  --backup=data/longvp-maintenance/EXAMPLE-backup/backup-manifest.json \
  --out=data/longvp-maintenance/EXAMPLE-apply \
  --stopped-proof=data/longvp-maintenance/stopped-proof.json
```

CLIは承認一覧のハッシュ、各候補ハッシュ、対象日・限月・出来高、既存のバックアップを検査する。
更新は元世代一致、作成は不存在条件で行う。
各書込み後にダウンロード・ハッシュ確認を行い、その後42日すべてについて
1分足合計・VP合計・complete・限月・承認出来高との一致を再確認する。
`EXAMPLE-apply/verified.json`が42件で揃い、不一致が0件であることを確認する。

承認期間の合計はNQ 13,357,979枚、GC 2,763,027枚。ただし合計だけでなく**各日一致**を必須にする。
対象外の日やprod/trades・coverage・rolls.jsonは反映しない。
別に再照合する場合は同じ引数で`--action=verify`を使う。

中断時：

- 同じrun／backup／候補で再実行する。反映済みファイルのrun印・ハッシュを照合し、加算や無条件再上書きはしない。
- `applied.json`は進捗記録。中断で最後の記録が欠けても、クラウド上のrun印とハッシュから同じ処理を再開できる。
- 新しい競合世代があれば強制実行しない。停止確認・並行保守・台帳を調べる。
- 42件の書込みは全体で原子的ではない。途中なら公開を戻さず、再開または復元して揃える。

## E. 直した版を再Publishする

42件照合が成功した後に限り、運用担当者が既存の公開手順で**修正版**を公開する。
このタスクでは公開操作を実行しない。
修正前の旧版を一時的につなぎ直すと、旧キャッシュから購入データを上書きする危険があるため避ける。
公開版が本流へ取り込まれた修正を含んでいることを、公開対象の版と起動ログで確認する。

## F. 起動後の確認

停止からここまでの実時間と、旧受信停止・新受信再開の時刻を記録する。

1. 認証済みの本番statusと稼働ログで、NQ・GC双方の上流受信・保存が進むことを確認する。
   エラーなしというだけでなく、保存件数・最終約定時刻・最新保存時刻が進んでいることを見る。
2. 42日を読み出し、承認数量が維持されていることを再確認する。
   起動時読み込み後・再集計後にも数量が減らないことを確認する。
3. LONG VPのstate／history／bootstrapが履歴の取り込みの完了を待つ旧ゲートに留まっていないことを見る。
   todayや7日再構築自体の履歴取得中はrunningであり得るため、state名だけで異常としない。
4. 取り込み中でも、次のCT16:55にlong_vp_day_saved／long_vp_day_preserved（mode: recorded_only、dateが対象取引日）が出ることを確認する。不完全保存はcomplete:false、より良い既存日次がある場合はpreservedであることを確認する。
   不完全ならgapsとcomplete:falseを確認し、CT17:05以降や後の直近7日再構築で改善することを見る。
   運用時間を変えるために本番時計を操作しない。16:55実機確認は次の該当時刻に行う。
5. history_request_failedにはsymbol・窓・elapsedMsがあり、大窓のnetwork_or_timeout後は小窓へ進むことを確認する。
   大窓を同じまま3回要求する旧挙動になっていないこと、失敗した最小窓はgapsに残り後続が進むことを見る。
6. GCのlong_vp_failedが出たら元例外とcauseを読めることを確認する。失敗を発生させるために本番APIや通信を壊さない。
7. 観測用ブラウザを使った場合は閉じ、プロセス終了と接続の後始末を確認する。

### 停止中に受信できない分

停止中はライブを受信しない。起動後、保存済みcoverageを復元し、不足部分を履歴RESTから取り直す。
直近3時間は起動時backfill（板・約定）の対象になり、LONG VPは直近7暦日の不足約定を対象に再取得する。
受信再開直後の未成熟な窓は終端後5分を待つため、公開が戻った瞬間に補完完了するとは限らない。

15〜25分程度の停止なら通常は上の対象範囲に収まる。
ただし上流履歴が利用でき、取得が成功することが条件。成功を保証して「欠けがなくなる」とは報告しない。
1分でも3回失敗すればgapとして残し、直近7日の再構築で再試行する。
7日を超えた分や上流で提供されない履歴は自動で埋まらない。
停止前後の該当UTC区間について、coverageと本番原約定の再保存を確認して補完完了とする。

## G. 戻す場合

公開を停止した保守状態を維持／再確認してから行う。候補ファイルが壊れていても原本バックアップだけから復元できる。

```sh
node server/tools/run-approved-longvp.ts \
  --action=restore \
  --backup=data/longvp-maintenance/EXAMPLE-backup/backup-manifest.json \
  --out=data/longvp-maintenance/EXAMPLE-restore \
  --stopped-proof=data/longvp-maintenance/stopped-proof.json
```

このrunが書いたままの対象に限って、元ファイルを条件付きで戻す。
元々なかった対象はこのrunの世代を条件付き削除し、元原本はSHA-256一致、新規対象は不存在を42件確認する。
別のwriterの更新やこのrunと異なるハッシュがあれば中断する。
バックアップを削除しない。復元後の版の公開判断は別に行い、自動で旧版を公開しない。

# HEATMAP 縮小時の線（2026-11-05）

ユーザー承認（案1）。縮小すると最大の板でも色が薄紫で止まる問題を直した。色の基準（上限・下限）の取り方は変えていない。

## 原因

- glow の描き方は、1つの価格を K 行に分けて描く（SPEC 7）。K は「1ティックの高さ（物理画素）」を丸めて 2〜10 に収めた値。
- 1ティックが1〜2.5画素だと K = 2 になる。このとき2行とも強さが 0.675 になり、芯の色の位置（t × 強さ）は最大でも 0.675 にしかならない。そのため最大の板でも `#b9aeff`（薄紫）で止まり、白・赤まで届かなかった。
- ユーザーの1枚目の画面は、256ティックを約538画素で描いていた（1ティック≒2.1画素）ので、これに当たっていた。

## 変更

1ティックが5画素（`MIN_LINE_PX`）未満のときは、glow に限って各価格を「太さ5画素の線」として価格の中心に描く。

- 線の行の強さは、今までと同じ式を K = 5 で当てる（`lineStrength`）。芯の行の強さは1になる。
- 線が重なった画素は「枚数×その行の強さ」が大きい価格を採る（同点なら強さの大きい線）。採った価格の枚数・強さ・時間の有効率を使う。色の基準に左右されない値なので、列のキャッシュはそのまま使える。
- この線モードでは、価格「自動」の面積平均は使わない（線ごとの値を保つ）。どの線も届かない画素は不明のまま。
- 1ティックが5画素以上のとき（拡大時）と `block` は、今までと同じ経路を通る。
- 今の板の色の帯も同じ線で描く（1画素1行、1:1で表示）。

## 確認

- `node --test test/*.test.ts`：204件合格（既存199件＋新規5件）。
- `pnpm run typecheck`：合格。`pnpm run build`：成功。
- `gpu-check.html` をヘッドレスの Chromium（SwiftShader の WebGL2）で実行：DPR1・DPR2 とも82項目すべて合格（画素差は最大2、許容3）。線モードの項目は、DPR1 で価格幅 40・60・100、DPR2 で価格幅 100。今の板の帯（価格幅100）は両方の DPR で線モード。
- ダミー（合成）データを実際の描画コードで描いた比較（`docs/evidence/zoom-lines/dummy-before-after.png`、スクリプトは `dummy-render.mts`）：
  - 拡大（20分×60ティック、1ティック11画素）は、修正前と後でバイト単位まで一致した。
  - 縮小（3時間×300ティック、1ティック2.2画素）は、修正前は最も明るい芯の色が `#b9aeff` だった。修正後は芯が `#ff3d2e`（赤）まで届く。
- 重さ（ダミー、node、CPU 経路、1400×660、3時間×300ティック）：全列を作り直す初回は 589ms → 685ms。色の基準だけを変えた再描画は 274ms → 276ms。
- 確認に使った Vite とブラウザは止めた。Chromium・Vite のプロセスがなく、ポートも閉じていることを確かめた。この確認ではサーバー（`/api/ws`）を起動していない。

## 未確認・残り

- 実データ・実ブラウザ（GPU 実機・iPad）での見た目と重さは確かめていない。
- 縮小時の色の基準（上限・下限が深い板に引っぱられる問題、原因2）はこの変更の範囲外。ダミーでは、深い板の壁は縮小後も目立ったまま（比較画像の④）。
- 試作にはなかった次の2点は、既存の決まりをそのまま当てている。
  - 板の出現・消滅のフェードは、線モードでも画素の行ごとに当てる。
  - 線モードでは、行ごとに勝った価格の時間の有効率を使う。
- `smoothing` を使わない比較専用の `GlowRaster` の経路（`glow.ts` の `frame`）は変えていない（画面からは使われない）。

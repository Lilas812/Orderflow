# AGENT_RULES.md — Replit Agent 作業ルール

このプロジェクトのすべての作業に適用する。指示文・仕様書と矛盾する場合は、作業を始めずに矛盾点を報告すること。

## 1. 仕様の優先順位

1. ユーザーがその回に出した指示
2. `docs/SPEC.md`（全体仕様）
3. `docs/UI_SPEC_HEATMAP.md`（画面仕様）
4. `replit.md`

- 1 と 2・3 が食い違う場合は、どちらにも従わずに止まり、食い違いを報告する。
- 仕様に書かれていない判断（ライブラリの追加、データ形式、閾値、色など）が必要になったら、推測で決めずに選択肢を示して質問する。
- 仕様の中で【未決定】【案】とある項目は確定ではない。勝手に確定扱いしない。

## 2. 作業範囲

- 指示されたフェーズ・タスクの範囲だけを作業する。先のフェーズの機能を作らない。「ついでに」の改善もしない。
- 指示に関係ないファイルは変更しない。整形・リネーム・リファクタリングも、指示がなければ行わない。
- 1回の依頼で扱うのは1つのタスクだけ。複数頼まれた場合は、順番を確認してから1つずつ進める。

## 3. 事前に許可が必要な変更

次の変更は、実施前に「何を・なぜ・影響範囲・元に戻す方法」を説明し、ユーザーの許可を得てから行う。

- すでに動いている機能の挙動が変わる変更
- ファイルやディレクトリの削除・移動、ディレクトリ構成の変更
- 依存パッケージの追加・削除・メジャーバージョン変更
- データ形式（保存ファイル、サーバー⇔ブラウザのメッセージ）の変更
- データベース・App Storage・デプロイ設定の変更
- `replit.md` の Current Status 以外の節、`docs/` 配下の仕様書の変更

## 4. 停止と報告

タスクが終わったら、必ずそこで止まり、次の形式で報告する。報告前に次の作業へ進まない。

```
## 報告
- 実施内容：（1〜3行）
- 変更ファイル：（パスと、各ファイルで何を変えたか）
- 確認手順：（ユーザーが自分で確かめる手順。開くURL、押すボタン、見るべきログ）
- 実行した確認：（実際に実行したコマンドと結果。実行していないものは書かない）
- 仕様との差分：（仕様どおりにできなかった点と理由。なければ「なし」）
- 未解決・懸念：（なければ「なし」）
- 次の候補：（提案のみ。実装はしない）
```

- 実際に実行していない確認を「確認済み」「動作します」と書かない。
- 推測で書いた部分は「推測」と明記する。

## 5. 不具合への対応

- 修正する前に、次を説明して許可を得る：再現手順、原因の仮説とその根拠（ログ・値）、修正方針、影響範囲。
- 同じ不具合の修正に2回失敗したら、3回目を試さずに止まり、分かったことと分からないことを報告する。
- 症状を隠す修正をしない（例外の握りつぶし、表示だけの辻褄合わせ、テストを通すためだけの条件分岐）。
- 不具合の調査のために一時的なログを足した場合は、報告にその場所を書く。

## 6. データの扱い

- 時刻は内部ではすべて「Unix エポックからのマイクロ秒（整数）」で持つ。外部から受け取った時刻の単位変換は、受信処理の1か所に集約する。単位を推測しない。
- 価格は内部では「価格 ÷ ティックサイズ」の整数で持つ（NQ のティックサイズは 0.25）。浮動小数のまま比較・集計しない。
- ダミーデータやモックを使うときは、画面とログに「ダミー」と明示し、本物のデータと混ぜない。
- 受信した生データを、確認できないまま加工・補完・捏造しない。欠損は欠損として扱い、ログに残す。

## 7. 外部接続

- TICK STREAM への WebSocket 接続はサーバーから1本だけにする。ブラウザから直接接続しない。
- 接続数の上限（L2 プランで3本）を超えないよう、再接続は指数バックオフで行い、古い接続を確実に閉じてから張り直す。
- サーバーからの `{"type":"ping"}` には `{"op":"pong"}` で応答する。
- `warning`（例：`ticks_lagged`）、`feed`、`error` のメッセージは捨てずにログに出す。

## 8. 機密情報

- APIキーは Secrets の `TICKSTREAM_API_KEY` から読む。コードに直書きしない。
- APIキーを含む URL・ヘッダー・環境変数の値をログ、画面、エラーメッセージ、報告に出さない。
- APIキーをブラウザに渡さない。

## 9. 確認とテスト

- 集計ロジック（板の更新、ヒートマップ列、デルタ、VP など）には、小さな入力と期待値を使った単体テストを付ける。
- 画面の変更は、何を見れば正しいと判断できるかを確認手順に書く。
- 仕様と違う実装になった場合は、隠さずに「仕様との差分」に書く。

## 10. 区切り

- タスクが1つ終わるごとに作業を区切り、チェックポイントで戻れる状態にする。
- 大きな変更の前には、現在の状態が動作することを確認してから着手する。

## 2. −5秒〜＋5秒の補正

定義：`アプリ時刻 + δ` とする。アプリのt秒の板をMBOのt+δ秒と比較する。
データの精度上、ここでは1秒刻み。ミリ秒の遅延/サンプリング位相の補正試験ではない。

端の欠けによる分母の差を避け、全11シフトで両側が存在する同じ32,341秒を主表とした。
通常の共通秒数はδ≤0で32,355、＋1〜＋5で32,354〜32,350。

## 3. ColumnAggregatorの代表値

`server/src/aggregate/columns.ts` の `accept` / `finish` を読み、集約器そのものもインポートして照合した。

- 各秒で `tsUs` が最大の受理済みsnapshotをそのまま採用。同時刻なら後から来たsnapshotで置き換える。
- 平均・最大数量・価格ごとの合成ではない。遅れて来た古い時刻のsnapshotは新しいpendingを置き換えない。
- 次秒の到着、秒開始から3秒後のexpire、履歴finish/flushで確定。
  expireは「3秒平均」を意味せず、既に確定した秒は後から変更しない。空白秒は埋めない。
- ライブのbook.tsは整数秒をus化するため、同じ秒に受理されたフレームでは最後の受理フレームになる。
  履歴は元のusの最大値。recvUsで選んでいるわけではない。

MBOはF_LASTで完了した注文更新だけを対象とし、同じ集約器でBBOを集約。
比較は元の品質マスク済みMBO板のある秒に限定し、観測のない秒の据置きを実受信と誤認しない。

| MBOの取り方 | 同じ32,355秒の両側一致% |
|---|---:|
| 元の1秒末尾板 | 12.3350 |
| 実ColumnAggregator・event時計で最後の完了板 | 12.3350 |
| event時計で最初の完了板（補助） | 10.2766 |
| Databento ts_recv時計で最後の完了板（補助） | 12.3381 |

ts_recvはDatabentoの受信時計であり、アプリのローカル受信時刻ではない。
eventLastと元の再構築板のBBOは比較対象全秒で一致。receive時計の差は両側一致で1秒分だけで、
実用上の大きな改善とは扱わない。

TICK STREAM L2文書はfull snapshot・symbol毎にcoalesce・最大およそ7回/秒と説明する。
「アプリが受け取った最後のフレーム」と「取引所の秒内の最終イベント」は必ずしも同じでない。
保存済み1秒列からは捨てられた中間フレーム/元subsecond時刻を復元できず、同じ集約器でも
配信元の入力フレームそのものまで一致させたとは主張しない。

## 4. 上下10/50段の価格・数量

「段」は各側の最良からN個の**正数量価格**であり、連続N ticksではない。
重なりは `|app topN ∩ MBO topN| / |app topN|` の全秒プール値。
Jaccardは交差/和集合。母数が足りない側は実在価格数を用いる。

数量比は同じアプリtopN価格の **MBO数量 / アプリ数量**。
相手側の探索はMBO保存窓全体（midから各側400ticks以内）で行い、同順位同士を割らない。
同価格がない場合は0として全分布に含め、欠け割合も別表示する。

## 5. implied

Databentoの現行GLBX.MDP3文書はMBOFD由来の個別注文と、MBP側で提供されるimpliedを区別する。
realとimpliedを結合した最良気配はCMBP-1/CBBOとして説明される。
通常のMBO/MBPとconsolidated schemaを混同しない。side=Nのimplied約定があること自体は、
MBOのresting orderに暗黙注文が含まれるという証明ではない。

TICK STREAMの公開L2文書は価格ごとの集約数量を説明するが、今回確認したL2/Symbols資料に
impliedの明示的な包含/除外条件はなかった。アプリのnormalization/Column保存もimpliedフラグを保持しない。
したがって **アプリ受信元がimpliedを含むかは未確認**。価格形状だけで確定しない。

同じ限月・同じ瞬間・同じreal bookに「impliedを追加するだけ」なら、買BBOを悪化させたり
売BBOを悪化させることはない。しかし比較秒の **86.472%** はアプリ買がMBOより低い、
またはアプリ売がMBOより高い。アプリのspreadも広い。
時刻/入力が同一という条件付きでは、implied追加だけを全不一致の説明にはできない。
逆に、位相差が残るためimpliedの寄与そのものを否定する根拠にもならない。

## 6. 学習とライブ判定の対応案

1. **定数時刻補正のみ：採用根拠なし。** 今回は0秒が最良。
2. **アプリ板を主要な学習・検証入力にする案を優先。** 同じ配信元・列化・欠け処理で
   研究データを揃える。将来の限月・元フレーム時計・受信/確定時刻の記録が必要なら別途承認を得る。
   今回は受信/保存の変更や新たな収集開始はしていない。
3. **MBOの直接転用は限定する。** raw数量、BBOから数ticks以内の絶対深度、
   キュー/注文イベント由来特徴を、そのままアプリ板で再現可能とみなさない。
4. 価格相対のやや広い帯、局所的な順位/分位、各データ内の数量正規化、変化率などを候補にできるが、
   「ずれに強い」と証明したわけではない。各側で数量比も異なるのでimbalanceまで自動的に頑健とはいえない。
   同時刻の対データで特徴差と判断差を測り、別日のアプリ板holdoutで評価してから可否を決める。
5. 配信元へimplied・数量定義・タイムスタンプとcoalesceの関係・過去の限月を確認できれば、
   未確定の原因をさらに絞れる。今回、認証APIや新規上流接続は使っていない。

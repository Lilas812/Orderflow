# 購入済みGC MBOの再構築・照合

## 1. 結論

**実データ取得・研究用の板再構築・照合済み。製品への組み込み・公開は未実施。**

- 対象Batch：`GLBX-20261105-RC8V97S64Y`。実際の購入は **GC.FUT** であり、NQではない。
- 期間：`[2026-09-30T00:00:00Z, 2026-11-04T00:00:00Z)`。
- 対象限月：raw `GCZ6`／既存購入約定の `GCZ26`。各日のDBN symbologyでinstrument IDを確認した。スプレッドと他限月は板に入れていない。
- 原本33ファイル、3,767,642,594 bytes。manifestは自身を除く32エントリーを照合。全33ファイルのSHA-256一致、原本は0444。
- 再構築：657個の時間ファイル、**2,349,863秒**、gzip後 **197,479,958 bytes**。
- 独立した全列読み戻しで、時刻順序・形式・正数量・価格順・正常BBOの違反は **0**。
- 既存購入約定と重なる506時間で、**2,009,413件・2,908,774枚**の秒・価格別件数／枚数が完全一致。方向別枚数も一致。
- 保存アプリ板との同秒比較は32,355秒。最良買い・最良売りの**同時一致率は12.335%**。同一の板／同一サンプリングであることは証明できていない。
- 限月選択・保存先・active指定・v2.2入力・製品コード・公開設定は変更していない。追加購入・新規Batch・ライブ接続・Publish・受信停止は実施していない。

## 3. 公式仕様と再構築条件

根拠：

1. [MBO snapshot](https://databento.com/docs/standards-and-conventions/mbo-snapshot)
2. [GLBX.MDP3の正規化・取引時間・implied book](https://databento.com/docs/venues-and-datasets/glbx-mdp3)
3. [DBN形式](https://databento.com/docs/standards-and-conventions/databento-binary-encoding)
4. [公式DBN MBOレコード定義](https://github.com/databento/dbn/blob/main/rust/dbn/src/record.rs)
5. [公式flags定義](https://github.com/databento/dbn/blob/main/rust/dbn/src/flags.rs)

- 過去MBOの日次スナップショットは平日00:00 UTC。週初めにはCMEの持ち越し注文のスナップショットもある。任意の途中時刻から空の板を仮定してはならない。
- スナップショットはclearの`R`と注文の`A`を用い、`F_SNAPSHOT`、`F_LAST`を確認する。生成されたスナップショットの`ts_event`は元注文の古い更新時刻になり得るため、これで並べ替えない。スナップショットの処理時計には`ts_recv`を用いる。
- 通常イベントはファイル順を維持し、同一instrumentの`F_LAST`までを一組として処理する。イベント途中の一時的な逆転を完成した板とは扱わない。
- `A`は追加、`M`は新しい絶対数量・価格への変更、`C`は取消数量の減算。`R`で当該限月の板をclearする。
- `T`は約定、`F`はfillの記述であり、これら自体では休眠注文を減らさない。対応する`M/C`でもう一度減らす二重処理はしない。
- CMEのMBOは明示注文。MBP側のimplied流動性と同一とは限らない。今回スプレッド注文を混ぜて暗黙注文を独自生成することもしていない。
- 休止・寄り付き前にはロック・逆転があり得る。今回、その秒は正常なヒートマップ列として出力せず、欠けとして残した。
- 回復不能な欠落を示す`MAYBE_BAD_BOOK`は別に検査する。対象限月を抽出した後のsequenceの飛びだけでは、他instrumentのメッセージと本当のデータ欠落を区別できない。

価格は`ナノ価格 / 100,000,000`でGCの0.10ティック整数に正確変換。order IDと元のナノ値はBigIntを用い、浮動小数点へ先に変換しない。
通常イベントのナノ秒を秒へ切り下げ、次の秒のイベントを適用する前に直前秒の最終状態を出力する。
仲値ティックを基準に、買い側400ティック、売り側400ティックの正数量を保存する。
同じ板が継続する秒は、完全に追跡できる注文状態を据え置く。**その秒に板メッセージが来たことを意味しない。**
初期状態不明・片側なし・不正状態は出力しない。欠損を前の板で推測補完していない。

ストリームで1日ずつ処理。RAMには現在の注文と価格集計だけを持ち、月全件のイベントや板を載せない。
日内の未圧縮時間ファイルをディスクに置き、gzip完了後に自分の一時ファイルを消す。

### 研究ツールの具体値

- `nice 19`、再構築のNodeヒープ上限512 MiB、ストリーム読取のRSSガード768 MiB。
- gzip level 6、sourceはhistory。これらは研究出力用で、製品の設定変更ではない。
- 固定限月GCZ26。自動ロール・価格調整・他限月接続はしない。
- 時刻が逆戻りして既出秒に影響する場合は、その範囲を除外する実装。今回該当0。

## 5. 期近限月の確認

GCZ6のinstrument IDは日別DBNマッピングから取得した（11/03は41271）。
全30 UTCファイルでGCZ6がアウトライトの最多T枚数だった。

さらに、保存済みT約定をAmerica/ChicagoのCT17:00〜翌16:00で集計し、24の完全なセッションすべてで、

> GCZ6の当該セッション枚数 ＞ 交差するUTC両日を合計した、他の全アウトライト限月の総枚数

が成立した。右辺は各競合限月の枚数より必ず大きい保守的な上界である。DSTもIntlのAmerica/Chicagoで処理。
この方法で、全raw MBOを再走査して各競合限月を再構築せずに、24セッションの最多を証明した。
購入期間の最初（CT09/29開始）と最後（CT11/03開始）は部分セッションであり、期間外を補わず部分として残す。

## 7. 既存購入約定との照合

元の購入済みCSVを変換した検証済みGCZ26ステージを再利用。全く同じ時刻・価格・枚数でも別行なら別件として加算し、集合化による重複削除をしていない。
CSV末尾は2026-10-30 00:00 UTC未満なので、それ以降には比較対象がない。

| 枚数 | 2,908,774 | 2,908,774 |

| 売り枚数 | 1,444,980 | 1,444,980 |
| 方向不明枚数 | 26,698 | 26,698 |
| 秒×価格の件数・枚数不一致 | 0 | 0 |
| 方向別枚数の不一致時間 | 0 | 0 |

方向不明はGCZ26のこの重複期間だけの値。過去の全限月等を含む調査の35,890件と同じ母集団と決めつけない。
Tの一致は時刻・価格・件数・数量の変換を強く裏付けるが、これだけで全ての板注文の正しさを証明するものではない。

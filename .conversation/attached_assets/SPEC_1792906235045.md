## 3. 全体構成【確定】

```
TICK STREAM ──(WebSocket 1本: 約定・板)──▶ サーバー（Node.js + TS, 1プロセス）
            ──(REST: 過去の約定・板)────▶   ├ ingest      受信・正規化
                                           ├ book        板の状態管理
                                           ├ aggregate   ヒートマップ列・集計・間引き
                                           ├ recorder    生データの保存（App Storage）
                                           ├ history     REST からの過去データ取得
                                           └ hub         ブラウザへの配信（WebSocket）
                                                 │
                                                 ▼
                                   ブラウザ（Safari / iPad / iPhone）
```

- TICK STREAM への WebSocket 接続はサーバーから1本だけ。ブラウザが何台つながっても増やさない。
- ブラウザは TICK STREAM に直接つながない。APIキーはサーバーだけが持つ。

## 5. TICK STREAM のデータ

### 5.1 分かっていること【確定】

- WebSocket：`wss://stream.tick-stream.xyz/v1/stream?key=…&symbols=NQ`。購読は `{"op":"subscribe","channel":"book","symbols":["NQ"]}` のような制御フレームでも行える。
- チャンネル：`ticks`（約定）、`book`（L2）。
- 約定フレームの項目：`type`, `symbol`, `price`, `size`, `side`（アグレッサー側 `buy`/`sell`）, `exch`, `ts`。
- 全フレームに `type` がある（約定も含む）。`welcome`、`feed`、`warning`、`error`、`ping`/`pong` がある。
- サーバーは15秒ごとに ping を送る。45秒応答がないと切断される。`{"op":"pong"}` で応答できる。
- 接続数の上限：L2 プランで3本。切れたソケットは最大45秒枠を占有する。超えるとコード 4029。
- 銘柄はルート指定（NQ）で、期近への乗り換えは自動。
- REST：`https://api.tick-stream.xyz/v1`、`Authorization: Bearer <key>`。
  - `GET /v1/ticks`（symbol, start, end）：start なしだと直近1時間のみ。7日前まで遡れる。
  - `GET /v1/history/ticks`（symbol, start, end, limit）：NQ の過去約定。
  - `GET /v1/history/book`（symbol, start, end, limit）：NQ の過去の板。
  - 範囲指定の start / end は Unix 秒。

### 5.2 Phase 0 で確定させること【要検証】

| 項目 | 確かめる内容 |
| --- | --- |
| 板メッセージの形式 | スナップショットか差分か、両方か。項目名、段数（片側何段か）、サイズ0の意味、通し番号の有無 |
| 時刻の単位 | WebSocket の `ts` は公式ドキュメントでは秒。SDK の説明では REST の約定はマイクロ秒。実データで突き合わせる |
| 板の更新頻度 | 1秒あたりのメッセージ数とバイト数（平常時・米国時間の寄り付き） |
| 板の段数 | 公式記載と実際の段数が違うという報告があるため実測する |
| 過去の板 | `/v1/history/book` の1行の形、1回の上限、ページ送りの方法、取得にかかる時間、粒度（毎更新かスナップショットか） |
| 保存容量 | 1時間あたりの生データ量（非圧縮・gzip） |

Phase 0 の結果は `docs/PHASE0_REPORT.md` にまとめ、この節に反映する（反映はユーザーの許可を得てから）。

## 6. 内部データ表現【確定】

境界（受信処理）で必ずこの形に変換し、以降は外部形式を使わない。

```ts
type TimeUs = number;      // Unix エポックからのマイクロ秒（整数）
type PriceTicks = number;  // 価格 ÷ ティックサイズの整数（NQ は 0.25）

interface Trade {
  tsUs: TimeUs;        // 取引所時刻
  recvUs: TimeUs;      // サーバー受信時刻
  price: PriceTicks;
  size: number;
  side: 'buy' | 'sell'; // アグレッサー側
}

interface BookLevel { price: PriceTicks; size: number; }

// 板の更新。形は Phase 0 の結果で確定する【要検証】
interface BookUpdate {
  tsUs: TimeUs;
  recvUs: TimeUs;
  isSnapshot: boolean;
  bids: BookLevel[];
  asks: BookLevel[];
}
```

- 時刻の単位変換は受信処理の1か所だけで行う。
- 価格の整数化も受信処理の1か所だけで行う。

## 7. ヒートマップの集計

- ヒートマップは「時間の区切り（列）× 価格」のマスに、板の枚数を持つ。【確定】
- 列の幅（何秒で1列か）：【未決定】。初期値の案は1秒。
- 1列の値の決め方：【未決定】。候補は次の3つ。
  - 区間の終わりの時点の枚数
  - 区間内の最大枚数
  - 区間内の時間加重平均
- 価格の丸め：ティック幅で丸める（参考記事の方式）。丸め幅は設定で変えられるようにする。【案】
- 色のスケール：【未決定】。候補は「上限で頭打ち」「対数」「上位◯%カット」。現在の板の棒の長さと同じ方式にそろえる。

## 8. サーバー → ブラウザの配信

- 方式：WebSocket（パス `/ws`）。最初は JSON、重ければバイナリに切り替える。【案】
- 間引き：板と約定は 100〜250ミリ秒ごとにまとめて送る。【案】

| メッセージ | 内容 | タイミング |
| --- | --- | --- |
| `hello` | 銘柄、ティックサイズ、列の幅、サーバー時刻 | 接続直後 |
| `history` | 直近 N 分のヒートマップ列と約定 | 接続直後 |
| `column` | 確定したヒートマップ列 | 列の区切りごと |
| `book` | 現在の板（間引き後） | 100〜250ミリ秒ごと |
| `trades` | 約定のまとめ | 100〜250ミリ秒ごと |
| `status` | 上流の接続状態、警告の件数 | 状態が変わったとき |

- 設定の読み書きは REST（`GET/PUT /api/settings`）。【案】

## 9. 保存

- 書き方：メモリにため、1〜5分ごとに gzip 圧縮した JSON Lines で書き出す。【案】
- 置き場所：`raw/{symbol}/{YYYY-MM-DD}/{HH}/{mm}.jsonl.gz` のように日付と時刻で区切る。【案】
- 開発中（Workspace）はローカルの `data/` に書いてよい。`data/` は Git の管理対象外にする。【確定】
- 自前で録画するかどうかは、`/v1/history/book` の結果で決める。過去の板が十分に取れるなら録画はキャッシュ程度にする。【未決定】
